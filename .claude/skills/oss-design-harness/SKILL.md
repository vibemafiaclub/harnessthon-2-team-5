# oss-design-harness

**어떤 주제의 PRD가 오더라도** 통하는 절차와 판단 기준만 담는다.

- **도메인 값(무엇을 만드는가)** 은 PRD에서 들어온다.
- **디자인 값(어떤 색·글자·간격을 쓰는가)** 은 `DESIGN.md`에서 들어온다.
- **이 문서에는 절차와 판단 기준만 있다.** 특정 서비스의 어휘·수치·화면 이름을 이 문서에 적지 않는다.

사용자는 **디자인 비전문가**라고 가정한다. 전문 용어를 모르고, 스스로 판단 기준을 언어화하지 못하며, 질문이 길어지면 지친다. 하네스의 품질은 결과물보다 **질문의 품질**에서 갈린다.

## 실행 원칙 (모든 단계 공통)

- **Figma MCP는 호출 예산이 있다.** (Pro·Full 좌석 기준 하루 200회·분당 10회) 노드를 하나씩 만지지 말고 화면/컴포넌트 묶음 단위로 실행한다. 작업 시작 전에 예상 호출 수를 사용자에게 알린다.
- 파일은 **Pro 등급 팀** 안에 있어야 한다. Starter 팀에서는 MCP가 동작하지 않는다.
- **토큰·변수를 바꾼 직후에는 반드시 스크린샷을 렌더한다.** 노드 속성 조회만으로는 대비 사고(검정 위 검정 등)가 검출되지 않는다.
- 최종 "이 정도면 됐다"는 판단은 항상 사람이 내린다. 하네스는 후보와 근거를 제시할 뿐이다.

## 이 하네스를 고칠 때

- **기록을 요구하는 규칙을 추가할 때는 반드시 기록할 자리(템플릿 칸)를 함께 만든다.
  쓸 자리가 없는 규칙은 실행 시점에 무시된다.**
  `brief.md` / `decisions.md` / `DESIGN.md` 템플릿의 칸은 이 문서가 "남긴다"고 요구하는 항목과 **1:1로 대응**해야 한다.
  규칙을 추가한 뒤 템플릿을 훑어 대응하는 칸이 있는지 확인한다. 없으면 규칙이 아직 완성되지 않은 것이다.
- 같은 이유로, **검증을 요구하는 규칙에는 검증 방법을 함께 적는다.** "확인한다"로 끝나는 규칙은 확인되지 않는다.
- 규칙은 **검증 가능한 문장**으로 쓴다. 부정형("~하면 실패")과 긍정형("~가 있는가")을 함께 둔다 —
  부정형만 있으면 "틀리지 않은 결과물"이 최대치가 된다.
- **표본 1건으로 규칙을 늘리지 않는다.** 한 프로젝트에서만 나온 발견은 기록해두고,
  다른 도메인에서 재현될 때 규칙으로 승격시킨다.

## 프로젝트별 DESIGN.md 생성 규칙

`DESIGN.md`는 프로젝트마다 새로 만든다. **없으면 화면을 만들기 전에 먼저 만든다.**

1. **입력 경로는 0-5 「디자인 방향 선택기」가 정한다.** 순서는 ① 프로젝트 기존 브랜드 시스템 →
   ② `oh-my-design.kr/builder`에서 사용자가 고른 레퍼런스의 `DESIGN.md` → ③ 사용자가 "모르겠다"면 하네스 추천 3개 중 하나.
   **하네스가 임의로 시스템을 정하지 않는다.** 사용자가 고르거나, 최소한 확인한 것만 쓴다.
2. 출처와 수집일을 적는다. **여러 개를 섞지 않는다.** 레퍼런스에서 가져온 특징은 `brief.md`에 따로 남긴다.
   레퍼런스의 로고·회사명·아이콘·이미지·카피는 가져오지 않는다.
3. `templates/design.md`를 복사해 채운다. 채워야 하는 것: 컬러 역할 토큰 · 타이포 · 간격 · 반경 · elevation · **아이콘 체계** · **표현 전략** · 제약사항 · 퀄리티 규칙.
4. **상태 토큰은 0-1에서 도출한 상태 집합에 맞춰 만든다.** 상태 수는 도메인마다 다르므로 템플릿의 예시 개수를 그대로 쓰지 않는다.
5. **브랜드색이 도메인 정서와 어긋나 보여도 색을 바꾸지 않는다.** 대신 **역할 배치**를 바꾼다 — 주 액션에만 남기고 상태·강조는 의미색으로 넘긴다. 색을 바꾸는 건 `DESIGN.md`를 교체하는 일이지 화면에서 할 일이 아니다.
6. 이 문서(`SKILL.md`)에는 디자인 값을 적지 않는다. 값은 전부 `DESIGN.md`에 있다.

# 0단계 — 요구사항 정렬

**항상 실행한다.** 사용자가 결정권자여도 생략하지 않는다. 결정권자라는 사실은 "기준이 이미 언어화돼 있다"는 뜻이 아니라 "기준을 물어볼 사람이 그 사람뿐"이라는 뜻이다.

## 0-1. PRD에서 화면 목록을 스스로 도출한다

처음 보는 PRD를 받았을 때 아래 순서로 화면을 뽑는다. 사용자에게 "몇 개 화면이 필요하냐"고 묻지 않는다 — 그건 하네스가 할 일이다.

1. **동사를 추출한다.** 기능 요구사항에서 사용자가 하는 행동을 동사로 끊는다. (등록한다 / 고른다 / 제안한다 / 모아본다 / 확정한다 / 공유한다 …)
2. **동사를 "한 화면에서 끝나는 결정 1개" 단위로 쪼갠다.** 한 화면에 결정이 둘 이상이면 나누고, 결정이 없는 화면은 다른 화면에 합친다.
3. **데이터 객체를 뽑는다.** PRD에 반복 등장하는 명사가 객체다. 객체마다 **목록 화면 + 상세 화면**이 후보로 생긴다. 객체 수가 적으면 목록만 남긴다.
4. **상태 전이를 뽑는다.** PRD가 "~한 것 / ~하는 중인 것 / ~끝난 것"을 구분하라고 요구하면, 그 상태 전부가 **한 화면 안에서 서로 구별되는지**를 화면 요건으로 적는다. 상태 하나가 화면 어디에도 없으면 요구사항 미충족이다.
   **상태마다 "지금 사용자가 할 일이 있는가"를 표시한다.** 이것이 강조 순서를 정한다 — 할 일이 있는 상태가 1순위, 기다리는 상태가 2순위, 끝난 상태는 약화한다. 할 일 있는 상태가 둘 이상이면 그중 **되돌릴 수 없는 손실이 큰 쪽**을 1순위로 올린다. 손실의 크기는 0-4 Q5(실수의 대가)의 답으로 판정한다. 상태 집합은 도메인마다 다르므로 이 순위표를 매번 새로 만들어 `brief.md`에 남긴다.
5. **역할을 뽑는다.** 사용하는 사람이 둘 이상이면(작성자/수신자, 관리자/참여자 등) **역할마다 진입 화면이 따로 필요한지** 판단한다. 필요하면 별도 화면으로 만든다.
6. **규모를 뽑는다.** PRD에 수치가 있으면(항목 N개, 기간 M주) **그 상한값으로 화면을 채워본다.** 상한에서 무너지면 화면 구조가 틀린 것이다.
7. **상한**: 주 화면 8~12장 + 상태 프레임(빈 / 로딩 / 오류 / 그 도메인 고유의 예외 상태). 이보다 많으면 2·3번에서 과분할한 것이다.

도출한 목록은 **화면 이름과 그 화면이 충족하는 PRD 요구사항 번호를 짝지어** 사용자에게 먼저 보여주고 시작한다.

## 0-2. PRD 반박 절차

**PRD를 그대로 따르지 않는다.** PRD는 문제 정의이지 설계안이 아니다. 아래에 걸리면 지적한다.

반박 트리거 — 하나라도 해당하면 반박 대상이다.

- PRD의 **기능 요구사항**과 PRD가 서술한 **사용자 상황**이 서로 어긋난다.
- 요구사항대로 만들면 PRD가 명시한 **규모(항목 수·기간·빈도)** 에서 화면이 무너진다.
- 요구사항이 **사용자가 가장 자주 마주치는 상태**를 다루지 않는다.
- 서로 다른 요구사항 둘이 **같은 화면에서 동시에 만족될 수 없다.**

절차:

1. **무엇이 충돌하는지** 한 문장으로 적는다. PRD의 어느 대목과 어느 대목인지 근거를 인용한다.
2. **대안을 2개** 제시한다. 하나는 PRD를 최대한 지키는 안, 하나는 요구사항을 바꾸는 안.
3. **사용자에게 고르게 한다.** 하네스가 임의로 PRD를 무시하지 않는다.
4. 반박 내용·근거·사용자의 결정을 **`brief.md`에 남긴다.**

**반박은 1~2개로 제한한다.** 전부 걸고 넘어지면 반박이 아니라 회피다. 가장 큰 충돌만 고른다.

## 0-3. 질문 설계 규칙

> **디자인 어휘를 갖지 않은 사용자에게 추상어로 묻지 않는다.
> 사용자가 실제로 써본 서비스를 기준으로 묻고, 미리보기를 보고 고르게 한다.**

**질문은 최대 6개.** 비전문가는 그 이상에서 지친다. 6개를 다 쓰지 않아도 된다.

| 규칙 | 나쁨 | 좋음 |
|---|---|---|
| **디자인 용어 금지** | "정보 밀도는 어느 쪽이 좋으세요?" | "한 화면에 다 보이는 게 나아요, 나눠 보는 게 나아요?" |
| **취향 말고 상황** | "어떤 느낌이 좋으세요?" | "이걸 언제 어디서 쓰게 되나요?" |
| **한 번에 하나** | 4개를 한꺼번에 나열 | 하나 묻고, 답을 받고, 다음으로 넘어간다 |
| **선택지 2~3개** | 자유서술만 요구 | 구체적인 두세 상황을 제시하고 고르게 한다 |
| **"모르겠다"를 유효한 답으로** | 답을 강요 | 기본값을 제시하고 "이렇게 갈게요, 이상하면 말해주세요" |

**금지어**: 정보 밀도 · 위계 · 톤앤매너 · 그리드 · 여백 · 대비 · 무드 · 컨셉 · 미니멀 · 모던 · 레이아웃 · 컴포넌트 · 플로우 · IA.
이 단어들이 질문에 들어가면 그 질문은 폐기하고 상황 질문으로 바꾼다.

**선택지는 라벨이 아니라 장면으로 쓴다.** "A안/B안"이 아니라 "화면을 열면 전부 한 번에 보이고 스크롤이 길어요" / "한 번에 하나씩 보이고 다음을 눌러 넘어가요"처럼 **사용자가 그 장면을 상상할 수 있게** 쓴다.

**"모르겠다"가 나오면** 기본값을 정해 말하고 반응만 받는다.
> "그럼 기본값으로 갈게요 — 처음 화면에서 지금 해야 할 일만 보여주고 나머지는 아래로 내립니다. 만들어서 보여드릴 테니 보고 말씀해주세요."

## 0-4. 질문 6개 (도메인 무관 템플릿)

PRD 내용으로 괄호를 채워 쓴다.

**질문하기 전에 PRD에서 답을 먼저 찾는다.** 6개 중 PRD가 이미 답한 것은 **묻지 않는다.** 읽은 답을 한 줄로 확인만 받는다 — "PRD 보니 몇 년씩 쓰는 앱이던데 맞나요?" 같은 식으로. 이미 적은 걸 다시 묻는 순간 사용자는 하네스가 PRD를 안 읽었다고 느낀다. **6개는 상한이지 목표가 아니다.** 실제로 던지는 질문은 대개 2~4개로 줄어든다.

**둘을 먼저 묻는다 — Q1(사용 상황)과 Q5(실수의 대가).** 이 둘이 화면 구조를 가장 크게 바꾼다. Q1은 첫 화면의 길이·터치 영역·탭 분리를 결정하고, Q5는 강조할 상태와 빈 상태 문구를 결정한다. 나머지는 **기본값으로 진행하고 화면을 보여준 뒤 반응으로 받는다** — 비전문가는 질문에 답하는 것보다 만들어진 화면을 보고 고치는 걸 훨씬 잘한다.

**질문 왕복은 3턴을 넘기지 않는다.** 터미널에서는 왕복 자체가 비용이다. 3턴 안에 못 채운 것은 전부 가정으로 기록하고 화면으로 넘어간다.

1. **사용 상황** — "이걸 주로 언제, 어디서 쓰게 되나요?" (예: 이동 중 잠깐 / 책상에 앉아서 오래)
2. **사용 지속** — "한 번 쓰고 끝나는 건가요, 며칠·몇 주 동안 계속 들어오는 건가요?"
3. **첫 화면의 목적** — "열자마자 제일 먼저 알고 싶은 게 뭐예요?" (선택지는 PRD의 데이터 객체로 만든다)
4. **한 화면 정보량** — "한 화면에 다 보이는 게 나아요, 하나씩 나눠 보는 게 나아요?"
5. **실수의 대가** — "여기서 뭔가 빠뜨리거나 잘못되면 뭐가 제일 곤란해요?"
6. **보여줄 일** — "이 화면을 다른 사람한테 보여주거나 같이 볼 일이 있나요?"

6번이 감성-도구 축을 대신한다. "혼자만 본다"면 도구 쪽, "남에게 보인다"면 표현 쪽으로 기운다. **"따뜻한 느낌이 좋으세요?"라고 묻지 않는다.**

## 0-5. 디자인 방향 선택기

"미니멀 · 모던 · 브루탈리즘"은 비전문가가 갖고 있지 않은 어휘다. 그 사람이 못 고르는 게 아니라
**물어본 방식이 틀린 것**이다. 대신 **그 사람이 실제로 써본 서비스**로 묻는다. 써본 앱에 대해서는 누구나 답한다.

### 선택 경로 — 이 순서로

1. **1순위 — 프로젝트에 기존 브랜드 시스템이 있으면 그것을 쓴다.** 이 경우 묻지 않는다.
2. **2순위 — 없으면 https://oh-my-design.kr/builder 에서 하나를 고르게 한다.**
   품질 등급이 매겨진 440개 회사 레퍼런스가 있고, 각 카드에서 그 회사의 `DESIGN.md`를 Export할 수 있다.
   카테고리(Fintech / Healthcare / Productivity / E-commerce / Developer Tools / Government / Education …),
   국가, 색 컨셉으로 좁힐 수 있다.
3. **3순위 — 사용자가 "모르겠다"고 하면 하네스가 3개를 추천한다.**

### 질문 형식

한 번만 묻는다. 문구는 이렇게 시작한다.

> "이 서비스의 기본 디자인 기준을 고를까요?
>  서비스 내용에 맞는 3개를 추천할게요.
>  또는 oh-my-design에서 마음에 드는 걸 직접 골라도 됩니다.
>  '잘 모르겠어요'를 고르면 제가 하나 추천할게요."

- **440개를 그대로 나열하지 않는다.** 비전문가가 지친다. 사이트 링크는 주되, 목록을 옮겨오지 않는다.
- **추천 3개는 PRD 도메인에 맞춰 매번 새로 고른다.** 사이트 카테고리와 PRD 도메인을 맞춰 좁힌 뒤 3개만 남긴다.
  지난 프로젝트에서 쓴 셋을 재사용하지 않는다.
- **각 후보에 취향 어휘가 아니라 체감으로 한 줄 설명을 붙인다.**
  - 좋음 — "당근 — 친근하고 말 걸듯" / "토스 — 깔끔하고 빠릿"
  - 나쁨 — "당근 — 웜 톤의 프렌들리 미니멀" (설명이 또 하나의 전문 어휘가 됐다)
- **세 후보는 서로 체감이 달라야 한다.** 비슷한 셋을 주면 고를 수 없다.

### 선택 후 처리

1. 선택한 레퍼런스의 `DESIGN.md`를 **프로젝트별 `DESIGN.md`의 출발점**으로 쓴다.
2. **PRD와 충돌하는 부분은 토큰값이 아니라 역할 배치부터 조정한다.** 색을 바꾸기 전에 그 색이 맡은 역할을 옮긴다.
3. **로고 · 회사명 · 실제 화면 구성 · 아이콘 · 이미지 · 카피는 복사하지 않는다.**
   `DESIGN.md`를 내보낼 수 있다는 것이 **원본 회사의 브랜드 자산까지 복제해도 된다는 뜻은 아니다.**
   디자인 판단의 참고 기준으로만 쓰고, 로고 · 아이콘 · 이미지 · 카피는 새로 만든다.
4. **"이 레퍼런스에서 가져온 특징"만 `brief.md`에 기록한다.**
   예: 정보 밀도 · 카드 구조 · 타이포 대비 · 색 사용량 · 아이콘 문법.
   회사명을 결과물의 근거로 쓰지 말고, **무엇을 가져왔는지**를 남긴다.
5. **사용자에게 한 줄로 확인받는다.** "이 톤으로 진행할게요."

## 0-6. 비전문가의 답을 디자인 결정으로 번역한다

답변 **원문을 그대로 남기고**, 그 아래에 번역을 적는다. 요약으로 대체하지 않는다 — 요약하면 뉘앙스와 함께 기준이 날아간다.

아래는 자주 나오는 표현의 표준 번역이다. 표에 없는 표현은 같은 방식으로 **검증 가능한 수치나 규칙**으로 바꿔 적는다.

| 사용자가 한 말 | 디자인 결정 |
|---|---|
| "복잡해 보여요" / "정신없어요" | 한 화면에 **동일 위계 항목 5개 이하**. 넘으면 그룹핑하거나 위계를 만든다 |
| "뭘 해야 할지 모르겠어요" | 화면당 **주 액션 1개**를 색·크기로 단독 구별. 경쟁 요소 제거 |
| "답답해요" / "빽빽해요" | 섹션 간격을 요소 간격의 **2배 이상**으로. 카드 내부 여백 상향 |
| "휑해요" / "허전해요" | 정보를 더 넣지 말고 **시각 요소**(아이콘·막대·아바타)를 추가. 여백은 유지 |
| "딱딱해요" / "사무적이에요" | 모서리 반경 상향 + 강조 색 1개 도입 + 문구를 구어체로. **장식 아이콘을 뿌리지 않는다** |
| "촌스러워요" / "싸구려 같아요" | 색 종류를 줄이고(역할 없는 색 제거) 그림자를 약화. 그라디언트 제거 |
| "글씨가 안 보여요" | 본문 대비 **4.5:1** 이상, 본문 최소 **14px** |
| "찾기 힘들어요" | 검색·필터를 화면 상단 고정. 목록에 그룹 구분 추가 |
| "한눈에 안 들어와요" | 제목과 본문 크기 차이 **1.5배 이상**. 요약 지표를 최상단에 배치 |
| "실수할 것 같아요" | 되돌리기 경로 + 확인 단계 추가. 파괴적 행동은 주 액션 색을 쓰지 않는다 |
| "모르겠어요" | **가정으로 기록**하고 기본값으로 진행. `brief.md` 가정 로그에 남긴다 |

## 0-7. 가정 처리

확정되지 않은 정보는 침묵으로 넘기지 않고 `brief.md`에 **"이렇게 가정했습니다"로 명시**한다. 각 가정에 **뒤집혔을 때 영향 범위**를 같이 적는다. C단계에서 반복 실패하면 여기부터 되짚는다.

## 0-8. 참고 화면을 보여줘야 할 때

질문만으로 부족해 실제 화면을 보여줘야 한다면:

- **ASCII 와이어프레임으로 대신하지 않는다.** 선 굵기·여백·색·타이포가 사라진 도식에 대한 반응은 원본 화면에 대한 반응이 아니다.
- **실서비스의 이름과 URL을 제시하고 직접 보게 한다.** 어느 화면을 봐야 하는지 진입 경로까지 적는다. 컨셉 목업(Dribbble 등)은 쓰지 않는다 — 빈 상태·오류·긴 텍스트가 없어 마감을 판단할 수 없다.
- 스크린샷을 구할 수 있으면 `refs/`에 저장하고 **파일 경로를 알려준다.**
- 반응을 받기 전에 **"실제로 보셨나요"를 먼저 확인한다.**

## 산출물

`brief.md` (템플릿: `templates/brief.md`) — 화면 목록·PRD 반박 기록·질문 답변 원문·번역·가정 로그·확정 토큰 값

# B단계 — 발산·수렴

무엇을 만들지는 정해졌으나 어떻게 만들지 정답이 하나가 아닐 때 실행한다.

## 축을 PRD에서 도출한다

축은 미리 정해져 있지 않다. **이 PRD에서 정답이 갈리는 지점**을 찾아 축으로 세운다.

축의 조건:
- 서로 **독립**이어야 한다. 한 축의 선택이 다른 축을 결정하면 그건 한 축이다.
- 각 축은 **한 문장으로 양극단을 말할 수 있어야** 한다.
- 각 축은 **화면 구조를 실제로 바꿔야** 한다. 색만 바뀌는 건 축이 아니다.

도출 방법 — 아래에서 2~3개를 고른다.

| 후보 축 | 언제 이 축이 생기는가 |
|---|---|
| 정보량 (한 화면 통합 ↔ 단계 분할) | PRD가 다뤄야 할 데이터 규모를 명시했을 때 |
| 주도권 (A가 제안 ↔ B가 제안) | 사용자가 둘 이상이고 누가 먼저 움직이는지 안 정해졌을 때 |
| 표현 강도 (도구적 ↔ 표현적) | 결과물을 남에게 보여줄 일이 있을 때 |
| 진입 방식 (목록 우선 ↔ 할 일 우선) | 반복 사용이고 항목이 쌓일 때 |
| 상태 노출 (전부 노출 ↔ 현재만 노출) | PRD가 상태 구분을 요구했을 때 |

## 후보 생성

- 축마다 후보 **3개**를 병렬 생성한다. 순차 스케치를 흉내내지 않는다.
- 후보는 **전체 앱이 아니라 그 축이 가장 선명하게 드러나는 화면 1장**으로만 만든다.
- 상한: 축 3개 × 후보 3개 = 9장.
- 시간이 없으면 축마다 한 극을 **근거와 함께 선택**하고, 탈락 후보도 표로 남긴 뒤 완성 화면으로 확인받는다. 근거를 남기는 목적은 유지된다.

## 교차 비평 — 페르소나도 PRD에서 도출한다

**PRD의 사용자 역할에서 이해관계가 가장 반대인 둘**을 고른다. 없으면 "매일 쓰는 사람 / 한 번 들어왔다 나가는 사람"으로 만든다.

각 페르소나에 대해 적는다: 사용 빈도 · 한 번에 쓰는 시간 · 실패했을 때 잃는 것.

**한쪽에만 좋은 후보는 탈락**시킨다. 두 관점이 충돌하면 그 충돌을 `decisions.md`의 "남은 트레이드오프"에 남긴다.

## 산출물

`decisions.md` (템플릿: `templates/decisions.md`) — 축 도출 근거·축 조건 확인·페르소나 2인(빈도·시간·잃는 것)·축별 후보와 탈락 후보·선택 이유·남은 트레이드오프·C단계 라우팅 로그·재결정 로그

# HTML 초안 단계 — 화면을 먼저 세운다 (B단계 → A단계 사이)

디자인 도구를 쓰기 전에, 또는 도구를 쓸 수 없을 때 **HTML로 화면을 먼저 세운다.**
호출 예산을 쓰지 않고 구조·대비·여백을 검증할 수 있어, 도구 작업의 재작업량을 크게 줄인다.

## 저장 위치

- **HTML 초안은 임시 디렉터리가 아니라 프로젝트 폴더 안에 저장한다.
  사람이 브라우저로 직접 열 수 없으면 검증 단계가 성립하지 않는다.**
- 권장 위치: `output/<화면세트 이름>/`. 산출물(`.html`)과 렌더 결과(`.png`)를 같은 폴더에 둔다.
- 사용자에게는 **홈 디렉터리 기준 절대경로**를 알려준다. 상대경로나 샌드박스 경로만 주면 열지 못한다.
- 스크래치·임시 경로는 중간 계산에만 쓰고, **사람이 봐야 하는 산출물은 반드시 프로젝트 폴더로 옮긴다.**

## 토큰 선언

- 실제 색상값·간격값은 `:root`에서 **한 번만** 선언한다.
- 컴포넌트 규칙에서는 실제 값을 다시 쓰지 않고 `var(--토큰명)`만 쓴다.
  금지하는 것은 컴포넌트 내부의 반복 하드코딩이다.
- 완성 후 `:root` 블록 밖에 남은 색상 리터럴이 있는지 기계적으로 확인한다. 1건이라도 있으면 고친다.

## 렌더 검수

- **파일을 만든 것으로 끝내지 않는다. 브라우저 크기로 실제 렌더해서 눈으로 본다.**
  헤드리스 브라우저 스크린샷이면 충분하다. 웹폰트·아이콘 로드를 기다릴 시간을 준다.
- 렌더를 보고 C단계 「평범함 판정」을 그대로 적용한다. 특히 **대비는 렌더 후에만 잡힌다** —
  값으로는 통과처럼 보여도 실제 화면에서 안 읽히는 조합이 나온다.
- 외부 CDN 자산(아이콘 폰트 등)을 쓰면 **오프라인에서 안 보인다는 사실을 사용자에게 함께 알린다.**

# A단계 — 구조적 사실 검증

화면이 다 만들어진 뒤, 스크린샷 없이 노드 속성만으로 예/아니오·수치로 검증한다.

- [ ] **토큰 밖 색상 0** — 모든 fill·stroke가 `DESIGN.md`에 정의된 토큰에 바인딩. 하드코딩 색이 1개라도 있으면 실패.
- [ ] **역할 없는 색 0** — 토큰 개수 자체는 제한하지 않는다. 다만 **모든 토큰이 "언제 쓰는지"를 `DESIGN.md`에 갖고 있어야** 한다. 설명 없는 토큰이 있으면 실패.
- [ ] **바인딩 리터럴 일치** — 변수에 바인딩된 paint의 리터럴 color가 변수 값과 다르면 실패. (Figma는 리터럴을 그대로 렌더한다. 바인딩만 걸고 리터럴을 검정으로 두면 검정으로 보인다.)
- [ ] **타이포 스타일 재사용** — `DESIGN.md`가 정한 개수를 넘지 않는다. 화면마다 새 사이즈를 만들면 실패. 스타일 미적용 텍스트가 있으면 실패. (아이콘 역할의 문자 노드는 예외로 두되 `DESIGN.md`에 명시)
- [ ] **간격 스케일 준수** — 모든 간격·여백이 `DESIGN.md`의 스케일 값에 속한다. 스케일 밖 값이 나오면 실패.
- [ ] **컴포넌트 재사용률** — 같은 모양이 두 번 이상 나오는데 인스턴스가 아니면 실패. 목표 70% 이상.
- [ ] **레이어 네이밍 semantic 여부** — 좌표·순번이 아니라 **역할**로 짓는다. `Rectangle 42` · `Group 7` · `Frame 1` 잔존 시 실패.
  - 화면 `Screen/<역할>` · 컴포넌트 `<종류>/<역할>` · 내부 슬롯 `#title` `#status` 형태
- [ ] **상태 커버리지** — 인터랙티브 컴포넌트는 `DESIGN.md`가 정한 상태 집합을 모두 갖는다. 데이터 화면은 `빈 / 로딩 / 오류` + **그 도메인 고유의 예외 상태** 프레임이 존재한다. **존재 여부만 본다. 품질은 C단계.**
- [ ] **오토레이아웃 적용** — 목록·카드·버튼에 절대좌표 배치 금지.
- [ ] **텍스트 오버플로 처리** — 그 도메인에서 나올 수 있는 **가장 긴 문자열과 가장 큰 수치**를 넣어도 잘리거나 밀리지 않아야 한다.
- [ ] **고정 요소 겹침** — 하단 고정 내비·고정 액션바가 있으면, 스크롤 콘텐츠 하단 여백이 그 높이 이상이어야 한다. 콘텐츠가 가려지면 실패.
- [ ] **터치 영역** — 누를 수 있는 요소가 44×44 미만이면 실패.

기준 수치는 `DESIGN.md`와 0단계 답변에서 온다. 이 문서에 프로젝트별 수치를 적지 않는다.

# C단계 — 미적·게슈탈트 판단

**반드시 스크린샷을 렌더해서 실제로 보고** 판단한다. 노드 속성 조회로 대체할 수 없다.

## 위계와 리듬

- [ ] **0.5초 안에 "지금 뭘 하라는 건지"가 잡히는가.** 잡히지 않으면 실패. 같은 무게의 요소가 3개 이상 경쟁하면 위계가 없는 것이다. 가장 중요한 요소는 크기·색·여백 중 **최소 두 가지**로 구별돼야 한다.
- [ ] **여백 리듬** — 수치가 맞아도 시각적으로 안 맞을 수 있다.
  - 텍스트 블록 여백은 바운딩 박스가 아니라 **글자(잉크) 기준**으로 본다. 위아래가 같은 값이어도 라인하이트 때문에 위가 떠 보인다.
  - 피사체가 배경 안에 들어가면 **투명 영역이 아니라 피사체 덩어리 기준**으로 상하 여백을 맞춘다. 한쪽이 다른 쪽의 2배를 넘으면 실패.
- [ ] **겹침·근접 충돌** — 텍스트는 어떤 요소와도 겹치지 않는다. 겹치지 않아도 **붙어 있으면 실패**다. 수치 레이블과 막대·축선은 최소 글자 높이의 절반만큼 띄운다. 읽혀도 붙어 있으면 고친다.
- [ ] **색온도·조명 일관성** — 한 화면에 따뜻한 회색과 찬 회색이 섞이면 실패. 그림자의 방향·세기가 요소마다 다르면 실패.

## 평범함 판정 — 실패를 면했는가가 아니라 탁월한가

다른 C단계 항목이 전부 통과해도 여기서 걸리면 **다시 만든다.**

**수치를 고정하지 않는다.** 배수·개수를 규칙으로 박으면 특정 장르의 취향이 하네스에 들어가고,
다른 도메인에서 어긋난다. 판정은 언제나 **그 화면의 목적** 기준이다.

### 먼저 이 화면의 1차 목적을 선언한다

목적을 적지 않고 판정하지 않는다. 목적에 따라 같은 화면이 통과도 되고 실패도 된다.

| 1차 목적 | 통과 조건 | 이 목적에서의 실패 |
|---|---|---|
| **빠른 처리형** — 한 손, 몇 초, 반복 사용 | 3초 안에 다음 행동이 잡힌다 | 3초 안에 안 잡히면 실패. **장식 요소가 있으면 그 자체로 실패. 히어로 영역은 불필요하다** |
| **현황 파악형** — 전체를 훑고 판단 | 전체 상태가 한눈에 잡힌다 | 한눈에 안 잡히면 실패. **비교가 필요한 숫자가 글자로만 나열돼 있으면 실패** |
| **선택형** — 후보 중 고르기 | 선택지 간 차이가 보인다 | 차이가 시각적으로 드러나지 않으면 실패 |
| **입력형** — 값을 넣기 | 입력 순서가 자연스럽다 | 순서가 부자연스러우면 실패. **히어로 영역은 불필요하다** |

한 화면에 목적이 둘 이상으로 보이면, 그건 화면을 쪼개야 한다는 신호다(0-1 2번으로 회귀).

### 목적을 도중에 바꿀 때

목적이 바뀌면 그 화면의 모든 판정 기준이 바뀐다. 그래서 목적 변경은 판정 결과보다 먼저 검증받아야 한다.

- **작업 도중 화면의 1차 목적을 바꾸려면 `brief.md`에 사용자 답 원문, 변경 이유, 그로 인해 포기한 것을 기록한다.**
- **사용자 답과 충돌하는 목적 변경은 사용자 답을 우선한다.**
- **근거 없이 목적이 바뀌면 그 이후의 모든 판정은 무효로 본다.** 판정을 다시 하는 게 아니라, 목적 선언으로 되돌아간다.

목적이 바뀐 줄 모르고 판정하는 경우가 가장 위험하다. 화면이 예뻐 보이도록 기준을 슬그머니 옮기는 일이
여기서 일어난다 — "빠른 처리형인데 히어로를 넣고 싶어져서 현황 파악형이라고 부르기 시작하는" 식이다.
목적을 바꾸고 싶어지면 **먼저 그게 사용자 답에서 나온 것인지 확인한다.** 아니면 화면을 고친다.

### 모든 목적에 공통

- [ ] **시선이 처음 닿을 지점이 없거나 둘 이상이면 실패.**
- [ ] **위계가 크기·색·여백 중 최소 두 가지로 표현되지 않으면 실패.** 배수는 고정하지 않는다 — 화면 목적에 맞게 판단하되, 훑었을 때 무엇이 중요한지 구별돼야 한다.
- [ ] **시각 요소를 넣었다면 "이게 없으면 이해가 느려지는가"를 자문한다. 아니면 제거한다.** 넣은 것 자체는 점수가 아니다.
- [ ] **여백이 균일하거나, 위계와 무관하게 배수만 맞췄으면 실패.** 여백은 정보 그룹의 경계와 일치해야 한다.
- [ ] **총괄 — 스크린샷을 보고 "전문 디자이너의 결과물로 보이는가"를 자문한다.** 아니면 원인을 진단해 **위 항목 중 어디에 걸리는지 지목한다.** "그냥 별로"로 끝내지 않는다.

이 판정은 `DESIGN.md`의 「표현 전략」 섹션과 짝이다. 그 섹션이 없으면 `templates/design.md`에서 먼저 만든다.

## 균일함(AI슬롭)의 5가지 신호

개별 요소는 멀쩡한데 전체가 "기계가 찍어낸 것" 같아 보이는 원인은 대개 균일함이다. 각각 독립적으로 실패 판정한다.

- [ ] **카드 균일** — 한 화면의 카드가 전부 같은 크기·라운드·그림자면 실패. 중요도가 다르면 최소 한 가지 속성이 달라야 한다.
- [ ] **강조 개수** — 화면당 강조 요소가 0개이거나 3개 이상이면 실패. 시선이 처음 닿을 곳은 정확히 하나. 강조색을 필터·배지·배너·본문에 동시에 쓰면 강조가 아니라 배경이 된다.
- [ ] **제목/본문 배율** — 제목과 본문의 크기 차이가 1.5배 미만이면 위계 부재로 본다. 굵기만 다르고 크기가 같으면 위계가 아니라 강조다.
- [ ] **시각 요소 부재** — 텍스트 블록만 세로로 쌓여 있고 시각 요소(아이콘·도형·차트·아바타·막대)가 하나도 없으면 실패.
- [ ] **여백 균일** — 여백이 전 구간 동일하면 실패. 섹션 사이는 요소 사이보다 최소 2배 벌어져야 한다.

## 시각 교정 기준

- [ ] **굵은 검정 테두리나 강한 그림자로 강조를 만들면 실패.** 일반 카드는 1px 중성 경계 또는 표면 차이로만 구분한다. 강조는 색·크기·배경으로 만든다.
- [ ] **선택 상태를 검정으로 칠하면 실패.** 선택은 브랜드 계열의 **연한 배경 + 진한 테두리/표시**로 만든다.
- [ ] **선택 표시가 표준 형태(체크박스·라디오)가 아닌 큰 단색 점이면 실패.** 무엇을 누르는 요소인지 형태로 읽혀야 한다.
- [ ] **본문·제목에 순수 검정(#000)을 쓰면 실패.** 짙은 중성색을 쓴다.
- [ ] **서로 다른 의미(충돌·경고·정보·완료·대기)에 같은 색과 같은 배지를 쓰면 실패.** 의미마다 색과 아이콘이 **함께** 달라야 한다. 색만 다르고 아이콘이 같거나, 아이콘만 다르고 색이 같으면 상태로 읽히지 않는다.

## 아이콘 원칙

- [ ] **아이콘만 있고 텍스트가 없으면 실패.** 아이콘은 정보를 대체하지 않고 보조만 한다.
- [ ] **한 화면에 아이콘·이모지 종류가 5개를 넘으면 실패.** 산만함으로 지각된다.
- [ ] **기능 아이콘과 장식 아이콘의 역할이 섞이면 실패.** 기능(내비게이션·액션)은 단색 라인, 강조·상태는 컬러 아이콘으로 역할을 나눈다.
- [ ] **아이콘을 이미지로 넣으면 실패.** 폰트 기반 문자 노드나 벡터로 넣어, 폰트·색 교체만으로 전체가 바뀌게 한다.
- [ ] **도메인 클리셰를 반사적으로 붙이면 실패.** 주제와 관련 있어 보인다는 이유만으로 장식 아이콘을 뿌리지 않는다.

## 매력 판정 — 부정형을 다 통과한 뒤에 적용한다

여기까지의 항목은 전부 **부정형("~하면 실패")** 이다. 부정형만 통과하면 **"틀리지 않은 화면"** 이 나오지
**"좋은 화면"** 이 나오지 않는다. 아래는 매력을 만드는 긍정형 기준이고, **이걸 통과해야 최종 PASS**로 본다.

- [ ] **이 화면에만 있는 것이 하나라도 있는가.**
  다른 앱에서 그대로 가져와도 어색하지 않다면 실패. 이 서비스의 정체성이 시각적으로 드러나는 지점이
  최소 하나 있어야 한다. 카드 + 배지 + 하단 탭 조합만으로는 어떤 서비스도 되지 못한다.

- [ ] **가장 중요한 수치가 압도적인가.**
  화면의 핵심 숫자는 주변 텍스트와 **2배 이상** 차이 나야 한다.
  **숫자와 단위·라벨을 같은 크기로 쓰면 실패.**

- [ ] **정보 종류가 다르면 형태도 다른가.**
  성격이 다른 항목(대기 / 완료 / 예외)이 **같은 카드 형태**를 쓰면 실패.
  색과 배지만 바꾸고 형태가 같으면 같은 것으로 읽힌다.

- [ ] **표면에 층이 있는가.**
  모든 영역이 같은 배경색이면 평면적이다. **최소 2단계의 표면 구분(배경 / 카드 / 강조)** 이 필요하다.

- [ ] **촌스러운 관습을 쓰지 않았는가.**
  **점선 테두리 · 무의미한 그라디언트 · 모든 카드 동일 그림자 · 이모지 남발은 즉시 실패.**

- [ ] **브랜드 요소가 화면 안에 살아 있는가.**
  로고나 색만 바꾼 게 아니라, 이 서비스의 성격이 **타이포 · 형태 · 아이콘 중 하나**에 반영돼야 한다.
  디자인 시스템 토큰을 그대로 쓴 것은 브랜드 표현이 아니라 규격 준수다.

존재 여부는 A단계에서 봤다. 여기서는 **그 화면이 실제로 쓸만한가**를 본다.

- [ ] PRD가 명시한 **최대 규모·가장 긴 문자열·예외 케이스**를 실제로 넣어보고 판단한다.

## 더미 콘텐츠 기준

빈칸을 `홍길동`·`Lorem ipsum`·`항목 1`로 채우면 완성도 판단이 불가능하다.

- 이름·명칭은 **그 로케일의 실제 분포**를 따른다. 길이를 섞는다(짧은 것·평균·아주 긴 것).
- 분류 라벨은 **PRD에 등장한 어휘**를 그대로 쓴다. 임의로 지어내지 않는다.
- 날짜·수량은 **PRD가 서술한 시점과 규모**에 맞춰 분포시킨다. 균등하게 뿌리지 않는다 — 실제 데이터는 몰린다.
- **예외 케이스를 반드시 섞는다.** 최댓값 1개, 최솟값 1개, PRD가 언급한 특수 케이스 1개.

# C단계 실패 시 라우팅

원인을 진단해 셋 중 하나로 분기한다. 합격/불합격만 내지 않는다.

1. **국소적 결함** — 표면 속성 하나의 문제. 그 속성만 고쳐 C단계 재검. B단계로 돌아가지 않는다.
2. **방향 자체가 틀림** — 국소 조정으로 안 고쳐지는 구조적 문제. B단계로 회귀해 다른 후보 선택 또는 재발산.
3. **반복 실패** — 후보를 바꿔도 같은 이유로 계속 탈락. 요구사항 해석이 틀렸다는 신호. 0단계로 에스컬레이션하고 `brief.md`의 가정 로그와 PRD 반박 기록을 재검토한다.

**재시도 상한: 3회.** 초과 시 사람에게 에스컬레이션하고 "무엇을 세 번 시도했고 각각 왜 실패했는지"를 함께 보고한다.

**매 회차를 `decisions.md`의 라우팅 로그에 남긴다** — 실패한 C단계 항목 · 진단(셋 중 하나) · 조치 · 결과.
기록하지 않으면 세 번째 시도에서 앞의 두 번을 재현하게 된다. 축 선택 자체를 뒤집었다면 **재결정 로그**에도 남긴다.

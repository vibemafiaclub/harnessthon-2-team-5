# oss-design-harness

현업 디자이너의 판단 기준을 추출해, Figma MCP로 실제 화면을 만들고 **게이트로 검증**하는 하네스.

전제(`docs/plan.md` 0장): 프롬프트는 가이드 준수를 보장하지 못한다.
보장하는 것은 게이트다 — 검사에서 걸리면 다음 단계로 넘어가지 않는다(fail-closed).

## 진실의 출처

모든 단계는 아래 파일만 판단 근거로 삼는다. **대화 맥락에서 기준을 추론하지 않는다.**

| 파일 | 역할 |
|---|---|
| `guide/core.rules.json` | L1 — 항상 적용되는 객관적 하한선. 프로젝트가 완화 불가 |
| `<project>/project.rules.json` | L2/L3 — 프로젝트별 값. 0단계에서 캘리브레이션 |
| `<project>/design-guide.md` | 사람이 읽는 디자인 가이드. 스키마: `templates/design-guide.md` |
| `guide/reference/toss.design.md` | 참조 디자인 시스템. **구조의 준거** — 색 값의 출처가 아니다 |

우선순위 충돌 시: **사용자 직접 지시 > 저장소 사실 > 위 계약 > 참조 영감.**

## 항상 지키는 5가지

이 하네스의 산출물 품질은 대부분 이 5개에서 갈린다.

1. **증거 등급을 붙인다.** 모든 값에 출처를 남긴다: `prd` / `repo` / `client-quote` / `measured` / `assumption` / `extension`.
2. **모르면 비운다.** 확인 안 된 값을 그럴듯한 기본값으로 채우지 않는다. 해결되지 않은 **가장 작은 단위만** 생략하고 Unknowns에 기록한다.
3. **표면을 섞지 않는다.** 모바일 제품 UI와 마케팅 웹을 별도 이름으로 유지한다. 서로 다른 두 값을 평균내지 않는다(16px + 7px → 11px 금지).
4. **없는 것을 지어내지 않는다.** 근거에 없는 카드·그림자·탭·토스트·다이얼로그를 업계 관행으로 채우지 않는다. 필요하면 `extension`으로 명시한다.
5. **구조는 베끼고 색은 도출한다.** 참조 시스템에서 가져오는 것은 **역할 구성·스케일의 모양·상태 계약·지오메트리**다. **색 값은 가져오지 않는다** — 색은 그 회사의 브랜드이고 그 도메인의 답이라, 복사하면 브랜드를 도용하는 동시에 0단계에서 뽑은 이 제품의 판단기준이 색에 반영되지 않는다. 팔레트는 PRD·클라이언트 반응에서 도출하고, 참조 팔레트는 `tokens._reference_palette`에 **금지 목록으로** 넣는다(`core.rules.json / no-reference-color-copy`).

## Figma 호출 규약

- `use_figma` 호출 **전에 반드시 `figma-use` 스킬을 먼저 로드한다.** 선택이 아니다.
- 새 파일이 필요하면 `create_new_file` 전에 `figma-create-new-file` 스킬을 로드한다.
- rate limit 때문에 검사는 **1회 호출로 전체 노드를 순회**한다. 규칙마다 따로 호출하지 않는다.

## 0단계 — 요구사항 정렬

무엇을 만들어야 하는지 자체가 불확실할 때 실행한다.

- **PRD가 있으면** `prd-to-design-guide` 스킬로 넘긴다. 이 단계를 중복 실행하지 않는다.
- **레퍼런스 소싱**: 같은 도메인의 실제 서비스 화면 3~5개를 모은다. 무드보드가 아니라 **비교 가능한 같은 종류의 화면**(예: 온보딩 3종)으로 모은다.
- **질문 형식**: 라벨형 질문("모던한 느낌 원하세요?") 금지. 레퍼런스를 보여주고 "좋다/싫다 + 이유"를 자유서술로 받는다. IA/플로우는 다이어그램이 아니라 클릭 가능한 로우파이 또는 시나리오 내러티브로 체험시킨다.
- **판단기준 역추출**: 자유서술에서 형용사가 아니라 **대조**를 뽑는다.
  - "좀 산만해요" → 정보밀도 하한 선호 → 첫 화면 결정 항목 ≤ 4
  - "이건 좀 딱딱해 보여요" → radius 하한 존재 → 최소 8px
  - 원문 인용을 `design-guide.md`에 `client-quote`로 남긴다. 요약하면 근거가 사라진다.
- **산출물**: `design-guide.md` (`templates/design-guide.md`) + `project.rules.json` + `brief.md`
- **게이트**: `status: "unfilled"`인 `blocker` 규칙이 하나라도 남아 있으면 W단계 진입 거부.

## B단계 — 발산·수렴

어떻게 만들지 정답이 하나가 아닐 때 실행한다.

- **독립 축 식별**: 후보를 가를 축을 2~3개 뽑는다(예: 비주얼 무드 / 정보 밀도 / 인터랙션 명시성). 축을 나누지 않고 화면 전체를 통째로 비교하면 무엇 때문에 선택했는지가 뒤섞여 근거가 남지 않는다.
- **후보 생성**: 축마다 2~3개. 축 하나만 바꾸고 나머지는 고정한다. 여러 축을 동시에 바꾸면 비교가 성립하지 않는다.
- **교차 비평**: 최소 2개 관점으로 본다 — 사용자 관점(과업을 끝낼 수 있는가) / 구현 관점(기존 컴포넌트로 만들 수 있는가).
- **산출물**: `decisions.md` (`templates/decisions.md`)

## W단계 / D단계 — 생성

**`references/레이아웃.md`를 읽고 시작한다.** 레이아웃 사고는 대부분 취향이 아니라 폭·높이 예산 문제라
사후에 발견하면 되돌리는 비용이 크다. 12개 항목 중 5개는 빌드가 거부해야 하는 것들이다.


W(와이어프레임)는 구조를, D(디자인)는 비주얼을 만든다. 지켜야 할 규칙이 다르므로 분리한다
(와이어프레임에서 색 대비를 검사하는 것은 무의미하고, 터치 타깃 크기는 구조 단계부터 확정되어야 한다).
규칙의 `stage` 필드가 현재 단계를 포함하지 않으면 **검사하지 않는다** — 통과가 아니라 평가 대상 아님이다.

## A게이트 — 구조적 사실 검증

노드 속성만으로 예/아니오 판정. 스크린샷 불필요.
항목은 `core.rules.json` + `project.rules.json`이 정의하고, 검사기가 실행한다.

- 컬러 팔레트 allowlist / 타이포 스타일 바인딩 / spacing 그리드 배수 / 컴포넌트 재사용률 / 레이어 네이밍 / variant 상태 커버리지
- `blocker`는 자동 수정 후 재검, `warning`은 기록만 하고 진행.
- 검사기가 아직 구현하지 않은 `blocker` 타입은 **사람 게이트로 승격**한다. "못 봤다"를 "통과했다"로 처리하지 않는다.
- 리포트 형식과 fail-closed 조건은 `guide/README.md`를 따른다.

## C게이트 — 미적·게슈탈트 판단

**`references/aesthetic-checks.md`를 읽고 그대로 판정한다.** 스크린샷 렌더 필수.
데이터 조회로 대체 불가이며, 스크린샷 없이 "괜찮아 보입니다"는 C단계 미수행으로 간주한다.

실패 라우팅(국소 수정 / B단계 회귀 / 0단계 에스컬레이션)과 재시도 상한 3회도 같은 문서에 있다.
최종 "이 정도면 됐다" 판단은 항상 사람이 내린다.

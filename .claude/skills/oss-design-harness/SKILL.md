# oss-design-harness

현업 디자이너의 판단 기준을 추출해, Figma MCP 또는 코드로 실제 화면을 만드는 범용 하네스다.

이 하네스는 특정 도메인, 브랜드, 플랫폼에 고정되지 않는다. PRD의 사실과 사용자의 반응을 우선하며, 프로젝트에 제공된 `DESIGN.md`는 증거 범위 안에서만 쓴다. 사례 시스템의 팔레트나 컴포넌트를 다른 제품에 자동 이식하지 않는다.

## 기본 디자인 원칙

- 한 화면에는 사용자가 지금 취해야 할 최우선 행동을 하나만 명확히 둔다. CTA는 스크롤·탐색 없이 식별 가능해야 한다.
- 정보와 조작을 줄여 사용자가 다음 행동을 추측하지 않게 한다. 보조 기능은 화면 계층 또는 progressive disclosure로 보낸다.
- Primary 색상은 최우선 CTA와 명시적 선택 상태에만 사용한다. 표면, 보조 텍스트, 보조 조작, 장식에는 secondary 색상을 사용한다.
- 프로젝트에서 Primary Action의 단색·그라데이션·상태값을 승인하면, 해당 값을 임의의 도형 색이 아니라 `Action/Primary` 토큰 또는 재사용 단위에 연결한다. 보조·파괴적·비활성 조작과 상태 표시에 무분별하게 전파하지 않는다.
- 정보는 둥근 사각형 안의 텍스트만으로 전달하지 않는다. 과업 이해에 도움이 되는 경우에만 아이콘, 아바타, 진행도, 구분선, 선택 컨트롤, 시간 시각화, 이미지, 그룹화된 리스트를 사용한다.
- 모든 객체를 카드로 만들지 않는다. 콘텐츠의 위계와 상호작용에 따라 plain content, list row, grouped/inset list, card, banner, sheet, media block을 선택한다. 관리·목록 화면은 스캔 밀도를 우선하고, 감정적 순간에만 여백·이미지를 더 크게 사용한다.

## 화면 범위와 수정 규율

- 사용자가 특정 화면 또는 프레임만 지시하면, 그 화면의 User Goal, 핵심 정보, Primary action, 필요한 상태를 먼저 적고 해당 범위만 수정한다. 사용자의 확인 전에는 다음 화면으로 넘어가지 않는다.
- Figma 변경 전에는 대상 프레임의 메타데이터, 기존 컴포넌트/스타일/Auto Layout 구조, 스크린샷을 확인한다. 기존 사용자 변경은 보존하고 가장 좁은 수정으로 해결한다.
- 변경 후에는 해당 프레임을 다시 캡처해 텍스트 잘림, safe area/탭 바 충돌, CTA 가시성, 여백, 상태 식별성을 확인한다. 캡처가 일시적으로 잘리거나 누락되면 구조를 먼저 점검하고 재캡처한다.
- 같은 역할의 표면·행·버튼·상태가 반복되면 그 규칙을 재사용 단위와 토큰에 승격한다. 다만 기존 화면 전체를 일괄 재배치하지 않으며, 명시적으로 요청된 범위 또는 계획된 리팩터링에서만 확장한다.

## 플랫폼별 적용 — Native iOS

PRD가 Native iOS를 대상으로 할 때만 다음 규칙을 적용한다.

- Apple HIG와 iOS/iPadOS UI Kit을 우선한다. 원격 Kit 컴포넌트를 가져올 수 없으면 Apple의 구조와 동작을 재현하고, 제한을 기록한다.
- iOS 시스템 타이포그래피와 SF Symbols를 사용한다. 새 표준 UI 아이콘에 emoji, Lucide, Material, custom icon을 섞지 않는다. SF Symbols를 사용할 수 없을 때는 다른 아이콘으로 대체하지 말고 슬롯/텍스트 구조를 보존한다.
- 기본 콘텐츠 여백은 16pt, 표준 아이콘의 상호작용 hit target은 최소 44 × 44pt로 시작한다. 카드·inset list 내부도 leading/trailing 16pt를 기본값으로 하고, 세로 여백은 콘텐츠 높이를 기준으로 시각적으로 대칭이 되게 한다.
- Root destination에만 bottom tab bar를 둔다. 각 탭은 같은 폭과 정렬 기준을 공유하고, 선택/비선택 상태는 같은 심볼 패밀리와 시스템 상태 색으로 구분한다. setup, detail, review, response 같은 navigation-stack 화면에는 탭 바를 강제로 넣지 않는다.
- 비-root back navigation은 44pt hit area의 iOS navigation pattern을 사용한다. 독자적인 원형 back-disc를 기본값으로 만들지 않는다.
- Primary CTA는 명확한 모서리 반경의 rounded rectangle로 만들고, bottom safe area와 tab bar 위에 충분한 여백을 둔다. pill 형태는 의도가 명확한 경우에만 사용한다.
- 상태·마감·경고·확정은 색만으로 전달하지 않는다. 의미 있는 SF Symbol과 텍스트를 함께 쓰고, 상태 background badge는 스캔에 실제로 도움이 될 때만 제한적으로 사용한다.
- 선택, 라디오, 토글, picker, alert, sheet, list row 등은 시스템 컴포넌트의 시각적 구조와 상태를 따른다. 임의의 장식적 컨트롤을 만들지 않는다.

## 표면·여백·상태 규칙

- 흰 캔버스에서 구분이 필요한 정보 묶음은 흰 surface, 1px의 절제된 border, 필요한 경우 낮은 elevation shadow로 분리한다. 그림자와 border를 중복 장식으로 과하게 쓰지 않는다.
- 카드 안의 첫·마지막 콘텐츠가 모서리나 border에 닿지 않도록 내부 padding을 확인한다. 목록 행의 아바타, 텍스트, trailing status도 동일한 inset 기준선에 맞춘다.
- 상태 라벨은 같은 화면에서 한 가지 구조(예: compact symbol + text)를 우선한다. 의미 없는 서로 다른 배경색 배지는 피하고, 상태는 label과 symbol로도 식별 가능해야 한다.

## 이미지와 더미 데이터 원칙

- 의미 있는 사진 영역은 비워 두지 않는다. 기본 사진 소스는 Unsplash, 보조 소스는 Pexels를 사용한다. 내용이 중요하지 않은 중립 placeholder에만 Lorem Picsum을 사용한다.
- 사진은 PRD의 실제 맥락과 레퍼런스의 사진 방향을 함께 만족해야 한다. 웨딩 제품에는 커플, 초대장, 식사, 꽃, 웨딩 장면처럼 제품 경험을 설명하는 이미지를 쓴다.
- 같은 경험 안에서는 조명, 채도, 피사체, 크롭, 비율이 일관된 사진을 선택한다. 의미 없는 장식 사진, 무관한 stock 이미지, 같은 사진의 반복은 피한다.
- 가상 사용자 아바타가 필요하면 DiceBear 등 일관된 시스템으로 만들고, 동일 인물은 모든 화면에서 같은 아바타를 유지한다.

순서를 그대로 따라가는 것이 아니라, 아래 4단계가 각각 무엇을 판단해야 하는지에 집중합니다.

## 0단계 — 요구사항 정렬

화면을 만들기 전, 무엇을 만들어야 하는지 자체가 불확실할 때 실행한다.

- **제품 모델 먼저 정의**: 화면 목록부터 만들지 않는다. 사용자 역할, 각 역할의 최종 목표, 핵심 객체, 객체 간 관계, 객체별 생명주기와 동시 관리 여부를 먼저 정리한다. 객체가 생성 후 다시 열리고 상태가 바뀐다면 해당 객체의 지속적인 detail 화면을 반드시 둔다.
- **화면 구조 도출**: PRD의 문장 수만큼 화면을 만들지 않는다. Entry/Home, collection/list, object detail, create/setup, status/progress, review/decision, time-based overview, completion 중 제품에 필요한 종류만 선택한다. 각 화면에는 이름, 사용자 목표, 핵심 정보, Primary action, 상태 변형, 진입점, 다음 목적지를 적는다. 독립된 목적이 없는 화면은 합치고, 중요한 상태에 집이 없으면 추가한다.
- **재방문과 예외 검증**: 사용자가 다음 날 다시 왔을 때 진행 중·완료된 객체와 다음 행동을 찾을 수 있는지, 여러 객체를 동시에 관리할 수 있는지, 비어 있음·미응답·마감·충돌·수정 같은 PRD 예외를 처리할 수 있는지 점검한다. 외부 참여자는 초대 링크 → 필요한 행동 → 완료 → 결과만 보이는 최소 경험으로 분리한다.
- **PRD 해석**: 사용자, 사용자 역할, 핵심 과업, 필수 데이터, 성공 조건, 예외 상황, 명시되지 않은 제약을 표로 분리한다. 화면 수나 레이아웃은 PRD에 없으면 가정으로 기록한다.
- **레퍼런스/시나리오 소싱 방법**: `https://recent.design/app-store-screenshots`에서 PRD와 가까운 카테고리 및 과업의 앱 스크린샷을 3개 이상 찾는다. 각 후보마다 "무엇을 차용할지"와 "무엇을 차용하지 않을지"를 한 줄씩 기록한다. 레퍼런스는 분위기 선택의 자극이며 요구사항의 근거가 아니다.
- **시스템 참고 우선순위**: 1) 사용자 지시와 PRD, 2) 기존 제품/저장소의 토큰·컴포넌트, 3) 프로젝트 `DESIGN.md`의 검증된 규칙, 4) Recent 레퍼런스, 5) Apple HIG. `DESIGN.md`에 대상과 맞지 않는 사례 규칙은 적용하지 않고 이유를 남긴다. Apple HIG는 모바일 탐색, 터치 목표, 시스템 상태, 접근성처럼 제품 고유 판단이 비는 부분을 보완할 때만 쓴다.
- **질문 형식**: 라벨형 질문 금지. 레퍼런스를 보여주고 "좋다/싫다 + 이유"를 자유서술로 받는다. IA/플로우는 다이어그램이 아니라 클릭 가능한 로우파이 또는 시나리오 내러티브로 체험시킨다.
- **판단기준 역추출 방법**: 반응을 관찰 가능한 규칙으로 바꾼다. 예: "복잡하다"는 말은 정보 밀도, 우선순위, 한 화면의 행동 수 중 어느 문제인지 되묻고, "따뜻하지만 유치하지 않게"는 색 사용량, 이미지 비중, 문장 톤, 장식 배제로 분해한다. 원문과 해석을 함께 `brief.md`에 남긴다.
- **가정 처리**: 확정 안 된 정보는 `brief.md`에 "이렇게 가정했습니다"로 명시한다.
- **산출물**: `brief.md` (템플릿: `templates/brief.md`)

## B단계 — 발산·수렴

무엇을 만들지는 정해졌으나 어떻게 만들지 정답이 하나가 아닐 때 실행한다.

- **독립 축 식별**: PRD에서 결과에 가장 큰 영향을 주는 축 2개만 선택한다. 후보는 보통 정보 구조/진입 흐름과 시각적 밀도/표현 방식으로 나누되, 실제 축은 도메인마다 새로 정한다.
- **후보 생성 방식**: 각 축에 2안씩 만든다. 전체 화면을 4안 이상 통째로 만들지 않는다. 한 후보가 바꾸는 변수는 하나로 제한하고, 공통 요구사항과 데이터는 동일하게 유지한다.
- **비교·수렴 방식**: 최소 두 관점으로 검토한다. (1) 사용자가 핵심 과업을 끊김 없이 끝내는가, (2) 이후 에이전트나 개발자가 토큰·컴포넌트·상태를 읽고 확장할 수 있는가. 선택 이유와 버린 안의 근거를 `decisions.md`에 남긴다.
- **산출물**: `decisions.md` (템플릿: `templates/decisions.md`)

## A단계 — 구조적 사실 검증

화면이 다 만들어진 뒤, 데이터로 예/아니오 또는 수치로 검증한다. 스크린샷 없이 Figma 노드 속성만으로 확인 가능.

체크 카테고리 (항목은 고정, 기준값은 프로젝트마다 `brief.md`에서 캘리브레이션):

- [ ] 컬러 팔레트 일관성 — 프로젝트 토큰 또는 승인된 값만 사용하고, 의미 없는 장식 색을 추가하지 않는다.
- [ ] 타이포 스타일 재사용 — 역할별 텍스트 스타일을 사용하며, 화면마다 임의 크기·두께를 만들지 않는다.
- [ ] Spacing 그리드 준수 — 기존 시스템이 없으면 4pt 단위를 기본 가정으로 `brief.md`에 기록한다.
- [ ] 컴포넌트 재사용률 — 반복되는 버튼, 행, 배지, 입력, 카드, 내비게이션은 인스턴스 또는 같은 구조의 재사용 단위로 만든다.
- [ ] 레이어 네이밍 semantic 여부 — `Screen/`, `Section/`, `Card/`, `ListItem/`, `Action/`, `State/` 접두어와 역할 이름을 사용한다.
- [ ] Variant 상태 커버리지 — 핵심 과업에서 실제로 필요한 default, selected, disabled, loading, empty, error, overdue/conflict 상태만 만든다. 존재하지 않는 상태를 관성적으로 추가하지 않는다.

## C단계 — 미적·게슈탈트 판단

화면이 다 만들어진 뒤, 반드시 스크린샷을 렌더해서 실제로 봐야 판단한다. 데이터 조회로 대체 불가.

체크 항목 (실제 스크린샷을 보며 판단):

- [ ] 섹션 간 색온도·조명 일관성 — 한 화면 안에서 서로 다른 브랜드의 그림자, 반경, 표면 처리를 섞지 않는다.
- [ ] 시각적 위계가 한눈에 읽히는가 — 첫 화면에서 현재 과업, 다음 행동, 위험 신호가 순서대로 읽혀야 한다.
- [ ] 여백 리듬의 체감 일관성 — 같은 역할의 요소는 같은 간격과 정렬 규칙을 공유해야 한다.
- [ ] 정보 밀도 번잡함 여부 — 사용자 과업과 무관한 요약 카드, 배지, 장식, 설명을 제거한다.
- [ ] 클리셰/AI슬롭 여부 — 과도한 그라데이션, 무관한 3D 일러스트, 과잉 카드화, 의미 없는 아이콘을 사용하지 않는다.
- [ ] 엣지케이스(빈 상태 등)의 실제 완성도 — 빈 상태는 다음 행동을 제공하고, 오류·충돌·마감 상태는 색만으로 전달하지 않는다.

### C단계 실패 시 라우팅

원인을 진단해서 아래 셋 중 하나로 분기한다.

1. **국소적 결함** (표면 속성 하나의 문제) → 그 속성만 고쳐 C단계 재검. B단계로 돌아가지 않는다.
2. **방향 자체가 틀림** (국소 조정으로 안 고쳐지는 구조적 문제) → B단계로 회귀, 다른 후보 선택 또는 재발산.
3. **반복 실패** (B단계에서 후보를 바꿔도 같은 이유로 계속 탈락) → 0단계로 에스컬레이션.

재시도 상한: 같은 원인으로 2회 수정 후에도 C단계를 통과하지 못하면 B단계로 돌아간다. B단계를 바꾼 뒤에도 2회 반복되면 0단계로 에스컬레이션한다. 최종 "이 정도면 됐다" 판단은 항상 사람이 내린다.

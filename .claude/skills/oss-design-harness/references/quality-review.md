# 모바일 디자인 품질 판정

HTML Q 단계와 최종 Figma A/C 단계에 적용한다. 면접 질문은 제작자가 답한다. 사용자는 실제 과업과 인상을 알려주며 전문 기준을 정할 책임을 맡지 않는다.

아래 평가표를 사용자에게 설문으로 전달하지 않는다. 과업은 '친구에게 초대를 보내보세요'처럼 이번 제품의 실제 상황 하나로 요청한다. 사용자가 막혔을 때 원인 분석·해결책을 요구하지 않고 행동을 관찰한 뒤 제작자가 수정안을 만든다. 실제 과업과 무관한 예시는 복제하지 않는다. 추천·조작 설명을 이미 들은 사용자의 수행은 설명 없는 첫 사용 검증으로 기록하지 않는다.

## 화면 먼저, 근거는 다음

1. 추천·설계 설명 전에 핵심 과업을 일상 언어로 제시하고 첫 행동, 현재 상태와 다음 행동의 이해, 완료·회복 여부를 관찰한다. 클릭이 없으면 위치 지목 검사라고 적는다. 도움을 준 시점, 이전 인터뷰 참여 여부를 기록한다. 선호와 과업 수행은 별개다. 에이전트의 예측은 사용자 관찰이 아니다.
2. 동일 콘텐츠와 모바일 폭에서 전체 화면과 필요한 세부 확대를 보고 비평한다. 장식용 기기 목업으로 잘림·밀도 문제를 숨기지 않는다. 설명 없이도 정보 관계와 시각적 조화가 성립하는지 본다.
3. 영향 큰 설계 결정만 아래 질문으로 검토하고, 불리한 콘텐츠·상태에서도 이유가 성립하는지 확인한다. 모든 토큰에 긴 설명을 붙이지 않는다.
4. 결함 위치·영향·수정 전후 캡처와 재검 결과를 연결한다. 수정으로 기존 장점이나 다른 상태가 깨지지 않았는지도 해당 범위에서 확인한다.

delivery.md의 과업별 시작 상태 → 행동 → 결과를 실제로 수행해 의미가 보존됐는지 확인한다. 레퍼런스와 닮았거나 클릭 효과가 있다는 이유로 업무 완료를 인정하지 않는다. 핵심 흐름을 막는 안내문 대체·잘못된 완료 표시·역할/권한 혼동은 수정 필요다. 합의된 전체 화면·필수 상태의 누락은 최종 D 검수에서 별도로 확인한다.

| 관점 | 제작자가 답할 질문 | 판정 증거 |
|---|---|---|

## 모바일 확인 범위

brief에 대상 플랫폼과 대표 뷰포트, 더 좁은 지원 폭을 정하고 이유를 적는다. 데스크톱 브라우저에서 보더라도 제품 영역은 모바일 폭으로 검증한다. 비교 보드의 바깥 배치는 제품 화면으로 평가하지 않는다.

플랫폼의 최신 공식 지침을 확인해 터치 영역, 텍스트 대비·크기, 뒤로 가기·내비게이션, 키보드·포커스, 안전 영역과 하단 고정 행동을 해당 과업에 적용한다. iOS/Android 관습을 근거 없이 혼합하지 않는다. 브라우저 시뮬레이션으로 확인한 것과 실기기 확인, 네이티브 동작 미검증을 구분한다. 모든 상태를 기계적으로 늘리지 말고 과업 실패·오해 가능성이 큰 상태를 먼저 검증한다.

## 판정과 증거의 한계

- 기준별로 충족 / 수정 필요 / 미검증과 평가 주체·증거를 적는다. 설명, 인기도, 사용자 선호, 노드 검사, 총점 중 어느 것도 다른 기준의 결함을 상쇄하지 않는다.
- 미감은 수치 일치만으로 충족시키지 않는다. 전체 구성이 의도한 인상을 만드는지, 어색한 지점과 채택 대안 대비 장점이 무엇인지 실제 화면으로 비평한다. 독립 디자이너 검토가 없으면 에이전트 자체 비평이라고 밝힌다.
- 기록상 사실(입력/속성/출처), 사용자 관찰(원문/실제 행동), 개선 가설(예상 효과/비평 해석), 미검증(미관찰 범위)을 구분한다. 같은 기록에 섞이면 절을 나눠 표기한다.
- 전문가 동등성·외주 금액·채용 성과는 이 내부 판정으로 입증하지 못한다. 향후 범위가 비슷한 전문 결과와 독립 비평을 통해 비교할 과제로 남긴다. 재실행 전에는 새 규칙의 효과도 미검증이다.

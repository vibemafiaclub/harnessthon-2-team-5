# PRD → 화면 목록 도출과 PRD 반박

> 출처: 팀 디자이너(noyunseo 브랜치) SKILL.md 0-1·0-2. 실제 청첩장·반려동물 두 도메인에서 검증된 절차.
> 0-A PRD 분석을 맡은 `design-judge` 브리프에 이 파일 경로를 넣는다. 사용자에게 "화면이 몇 개 필요하냐"고 묻지 않는다 — 그건 하네스가 할 일이다.
> 0-A judge 의 입력 화이트리스트는 PRD + 이 파일(+ 0-A2 가 병렬로 만든 `design/references.md` 는 0-F 에서)뿐이다. 그래서 반박 유형 정의(§2)와 필수 플로우 목록(§1-8)은 여기에 그대로 둔다 — SKILL.md 를 브리프에 얹지 않는다.

## 1. 화면 목록 도출 8단계

1. **동사를 추출한다.** 기능 요구사항에서 사용자가 하는 행동을 동사로 끊는다(등록한다 / 고른다 / 제안한다 / 모아본다 / 확정한다 / 공유한다 …).
2. **동사를 "한 화면에서 끝나는 결정 1개" 단위로 쪼갠다.** 한 화면에 결정이 둘 이상이면 나누고, 결정이 없는 화면은 다른 화면에 합친다.
3. **데이터 객체를 뽑는다.** PRD에 반복 등장하는 명사가 객체다. 객체마다 **목록 화면 + 상세 화면**이 후보로 생긴다. 객체 수가 적으면 목록만 남긴다.
4. **상태 전이를 뽑는다.** PRD가 "~한 것 / ~하는 중인 것 / ~끝난 것"을 구분하라고 요구하면, 그 상태 전부가 **한 화면 안에서 서로 구별되는지**를 화면 요건으로 적는다. 상태 하나가 화면 어디에도 없으면 요구사항 미충족이다.
   - **상태마다 "지금 사용자가 할 일이 있는가"를 표시한다.** 이것이 강조 순서를 정한다 — 할 일이 있는 상태가 1순위, 기다리는 상태가 2순위, 끝난 상태는 약화한다.
   - 할 일 있는 상태가 둘 이상이면 **되돌릴 수 없는 손실이 큰 쪽**을 1순위로 올린다. 손실의 크기는 인터뷰 **Q5(실수의 대가)** 답으로 판정한다. 인터뷰 전에는 가설로 적고 `[HYPOTHESIS]` 태그.
   - 상태 집합은 도메인마다 다르므로 이 순위표를 매번 새로 만들어 brief §2d(상태 강조 순위 — Q5 원문 ID 를 붙인다) 에 남긴다. 이것이 상태 색 토큰(brief §7)의 개수·이름·강조 순서가 된다. 순위표의 상태 하나하나가 §2c 의 '상태 순위표의 각 상태' 행에서 담당 화면 # 를 가져야 한다.
5. **역할을 뽑는다.** 사용하는 사람이 둘 이상이면(작성자/수신자, 관리자/참여자) **역할마다 진입 화면이 따로 필요한지** 판단한다. 필요하면 별도 화면. 역할은 §2 표의 '역할' 열에 화면마다 적는다(§11 '누가 쓰는가' 의 역할 명사와 대조 — B-3c). 인터뷰이(오너)와 다른 역할(초대받은 쪽·참여자)의 첫 진입 화면은 오너의 첫 진입 화면과 같다고 가정하지 않는다.
6. **규모를 뽑는다.** PRD에 수치가 있으면(항목 N개, 기간 M주) **그 상한값으로 화면을 채워 본다.** 상한에서 무너지면 화면 구조가 틀린 것이다. 이 상한이 2단계 더미 데이터의 규모가 된다.
   - 6b. **레퍼런스 대조.** `design/references.md` 가 입력에 있으면(0-F 에서 §2 를 확정할 때) 화면마다 같은 1차 목적의 REF 행을 ≥1 짝짓고, 진입·1등 정보·상태 표현이 다른 곳을 한 줄로 적는다. 이유 없이 다른 것이 신호다 — `[PRD 반박 트리거 후보]` 로 표시하고 §2 트리거 표에 대조한다. 레퍼런스에서 가져오는 것은 패턴(같은 과업을 어떻게 푸는가)뿐이다 — 색·간격·서체 같은 값은 가져오지 않는다. 짝지을 REF 행이 하나도 없는 화면은 '레퍼런스 없음' 으로 적고 넘어간다(반박 사유가 아니다).
7. **상한**: 주 화면 8~12장 + 상태 프레임(빈 / 로딩 / 오류 / **그 도메인 고유의 예외 상태**). 이보다 많으면 2·3번에서 과분할한 것이다. `agent_flow_candidates_max` 안에서 후보를 낸다.
8. **필수 플로우 대조.** PRD 와 무관하게 아래 여섯 항목마다 **화면 있음(#)** 또는 **해당 없음 — 사유** 를 적는다. PRD 가 침묵한다는 것은 화면이 필요 없다는 뜻이 아니다.
   - (a) 첫 진입·온보딩(등록 0건인 첫 화면 — 다음 행동 문구가 있는가)
   - (b) 초대 보내기·공유(사용하는 사람이 둘 이상이면 필수 — 링크·초대 행위·참여자 관리)
   - (c) 초대받은 쪽 첫 진입(미가입 상태에서 링크를 열었을 때 보이는 화면)
   - (d) 역할별 랜딩(5단계에서 역할이 둘 이상이면 역할마다)
   - (e) 알림·리마인드 진입(알림을 눌러 들어왔을 때 도착하는 화면)
   - (f) 설정·탈퇴
   PRD 에 없는데 필요하면 §2 에 `X-nn` 화면으로 올리고 §10 에 유형 `누락` 행(P-nn)을 만든다 — 트리거는 '필수 플로우 부재'. 이 여섯 항목은 brief §2c 의 앞 6행과 1:1 이다. §2c 의 나머지 3행(상태 순위표의 각 상태 / 시나리오 까다로운 상황 / 되돌리기·오류 복구)은 4단계 순위표·시나리오·7단계 상태 프레임에서 채운다. 되돌리기·오류 복구 행은 오류 상태 프레임과 되돌리기 경로(확인 단계·취소)가 어느 화면에 있는지를 적는다.

도출한 목록은 **화면 이름과 그 화면이 충족하는 PRD 요구사항 번호를 짝지어** 표로 만든다. PRD 번호가 안 붙는 화면은 §10 누락 번호(P-nn)를 대신 붙인다 — §2 매핑 열 표기는 `X-nn → §10 P-nn`. 번호가 아예 없는 화면은 없어야 하고, 어느 화면에도 안 붙는 요구사항 번호도 없어야 한다(2단계 종료조건이 이 표를 대조한다). 완전성의 기준은 PRD 기능 번호 + 8단계 필수 플로우 둘 다다 — PRD 번호만 100% 맞아도 8단계에 빈 칸이 있으면 미완이다.

## 2. PRD 반박 트리거 5개

PRD는 문제 정의이지 설계안이 아니다. 아래에 하나라도 걸리면 반박 대상이다.

| 트리거 | 뜻 |
|---|---|
| **기능 ↔ 상황 어긋남** | PRD의 기능 요구사항과 PRD가 서술한 사용자 상황이 서로 맞지 않는다 |
| **규모에서 무너짐** | 요구사항대로 만들면 PRD가 명시한 규모(항목 수·기간·빈도)에서 화면이 무너진다 |
| **최빈 상태 미처리** | 요구사항이 사용자가 가장 자주 마주치는 상태를 다루지 않는다 |
| **동시 만족 불가** | 서로 다른 요구사항 둘이 같은 화면에서 동시에 만족될 수 없다 |
| **필수 플로우 부재** | §1 8단계 항목(첫 진입·초대 보내기·초대받은 쪽 진입·역할별 랜딩·알림 진입·설정·탈퇴)이 PRD 에도 화면표에도 없다 |

우리 유형 태그(`문제`/`누락`/`과잉`)와 함께 쓴다. 트리거는 "왜 반박인가", 유형은 "무엇을 바꾸자는 것인가"다. 유형 정의(design-interview SKILL.md 0-A 요구 산출 6번과 같은 문장 — judge 화이트리스트에는 이 파일만 있으므로 여기에 둔다):

- `문제` — 그대로 만들면 사용자 경험이 나빠지는 요구
- `누락` — PRD 에 없지만 있어야 사용자 여정이 이어지는 것
- `과잉` — 있어도 가치가 낮아 빼는 게 나은 것

'필수 플로우 부재' 트리거는 항상 유형 `누락` 이다. 반박 목록에는 `누락` 유형이 ≥1 있어야 하고, 정말 없으면 '누락 없음 — 사유' 를 쓴다(check-brief B-12 가 센다). PRD 가 이미 말한 것을 뒤집는 `문제` 형만 있고 `누락` 형이 0 이면 PRD 침묵 영역을 보지 않은 것이다.

## 3. 반박 절차

1. **무엇이 충돌하는지** 한 문장. PRD의 어느 대목과 어느 대목인지 **원문 인용**. `누락` 유형은 인용 대신 'PRD 가 침묵하는 곳: <8단계 항목 또는 시나리오 장면>' 을 쓴다.
2. **대안을 2개** 제시한다. 하나는 PRD를 최대한 지키는 안, 하나는 요구사항을 바꾸는 안. `누락` 유형은 '화면을 넣는 안 / 없이 가는 안'.
3. **사용자에게 물을 쉬운 말** 한 문장 — 디자인 용어 없이(금지어 14개, `scripts/lib/forbidden-words.js` 정본) 상황 예시로, **하네스 추천을 문장 안에 먼저 포함한다**(결정형 호출). 형식: "PRD에는 X라고 되어 있는데, 실제로 쓰다 보면 Y한 상황이 생길 것 같아요. **저는 Z 가 낫다고 봅니다 — 이유.** 그래도 PRD 대로가 나은 경우가 있을까요?" `누락` 유형은 "PRD 에는 없지만 실제로 쓰다 보면 Y 를 해야 할 때가 올 것 같아요. **저는 그 화면을 넣는 쪽이 맞다고 봅니다 — 이유.** 없어도 될까요?" 형. **추천 없는 양자택일은 결정 위임이지 반박이 아니다.** 항목마다 `recommended`(대안 A/B/PRD대로 중 하나)와 `why`(이유 한 줄)를 적는다 — 0-B 가 pushback 질문의 `text`·`recommended`·`why` 로 그대로 옮기고(다시 쓰지 않는다), brief §10 의 '하네스 추천'·'이유' 열이 된다.
4. **사용자는 추천에 동의하거나 다른 쪽을 고른다.** 하네스가 임의로 PRD 를 무시하지 않는다. 미응답·모르겠음은 **추천 채택 + brief §6 '사용자 위임'** 으로 기록한다(state `human_gates.delegations[]` kind `unknown`). 결정을 brief §10 에 남긴다 — '사용자 확인 원문' 열에는 답 원문(A-nn) 또는 '사용자 위임'.

**반박은 상한 안에서 가장 큰 충돌부터.** full ≤`agent_prd_pushback_max`(10), fast ≤4이되 실제로 묻는 것은 1~2개 — 그 중 `누락` 형 ≥1, `문제` 형 ≤1. 전부 걸고 넘어지면 반박이 아니라 회피다.

## 4. 실측 예 (형식 참고 — 내용은 다른 도메인)

반려동물 복약 PRD의 "오늘 복약 체크" 요구는 **"안 줬다"와 "줬는데 체크를 안 했다"를 구분하지 못해** 유저스토리 1(중복 투약 위험)을 오히려 유발한다 → 트리거 "동시 만족 불가" · 유형 `문제` → 대안 A: 체크박스 유지 + 확인 단계 / 대안 B: 체크박스를 "내가 줬어요" 기록 행위로 변경 → 하네스 추천 B(이유: 체크가 곧 '줬다' 기록이 되어 두 상태를 구분할 필요 자체가 없어진다) → 물을 쉬운 말: "체크만 해 두면 '안 준 건지 체크만 빠뜨린 건지' 헷갈릴 수 있어요. 저는 체크 대신 '내가 줬어요' 버튼이 낫다고 봅니다 — 누른 순간이 기록이 되니까요. 그래도 체크박스가 나은 경우가 있을까요?" → 사용자 선택 B.

`누락` 형 예: 같은 PRD 가 초대 화면을 말하지 않는데 사용자는 둘(보호자 둘) → 트리거 "필수 플로우 부재" · 유형 `누락` → §2 에 `X-01 초대 링크 보내기` + §10 `P-01` → 물을 쉬운 말: "PRD 에는 없지만 다른 보호자를 부르려면 링크를 보내는 화면이 있어야 할 것 같아요. 저는 넣는 쪽이 맞다고 봅니다 — 없으면 두 사람이 같은 기록을 볼 수가 없어서요. 없어도 될까요?"

# PRD → 화면 목록 도출과 PRD 반박

> 출처: 팀 디자이너(noyunseo 브랜치) SKILL.md 0-1·0-2. 실제 청첩장·반려동물 두 도메인에서 검증된 절차.
> 0-A PRD 분석을 맡은 `design-judge` 브리프에 이 파일 경로를 넣는다. 사용자에게 "화면이 몇 개 필요하냐"고 묻지 않는다 — 그건 하네스가 할 일이다.

## 1. 화면 목록 도출 7단계

1. **동사를 추출한다.** 기능 요구사항에서 사용자가 하는 행동을 동사로 끊는다(등록한다 / 고른다 / 제안한다 / 모아본다 / 확정한다 / 공유한다 …).
2. **동사를 "한 화면에서 끝나는 결정 1개" 단위로 쪼갠다.** 한 화면에 결정이 둘 이상이면 나누고, 결정이 없는 화면은 다른 화면에 합친다.
3. **데이터 객체를 뽑는다.** PRD에 반복 등장하는 명사가 객체다. 객체마다 **목록 화면 + 상세 화면**이 후보로 생긴다. 객체 수가 적으면 목록만 남긴다.
4. **상태 전이를 뽑는다.** PRD가 "~한 것 / ~하는 중인 것 / ~끝난 것"을 구분하라고 요구하면, 그 상태 전부가 **한 화면 안에서 서로 구별되는지**를 화면 요건으로 적는다. 상태 하나가 화면 어디에도 없으면 요구사항 미충족이다.
   - **상태마다 "지금 사용자가 할 일이 있는가"를 표시한다.** 이것이 강조 순서를 정한다 — 할 일이 있는 상태가 1순위, 기다리는 상태가 2순위, 끝난 상태는 약화한다.
   - 할 일 있는 상태가 둘 이상이면 **되돌릴 수 없는 손실이 큰 쪽**을 1순위로 올린다. 손실의 크기는 인터뷰 **Q5(실수의 대가)** 답으로 판정한다. 인터뷰 전에는 가설로 적고 `[HYPOTHESIS]` 태그.
   - 상태 집합은 도메인마다 다르므로 이 순위표를 매번 새로 만들어 brief §2 에 남긴다. 이것이 상태 색 토큰(brief §7)의 개수·이름·강조 순서가 된다.
5. **역할을 뽑는다.** 사용하는 사람이 둘 이상이면(작성자/수신자, 관리자/참여자) **역할마다 진입 화면이 따로 필요한지** 판단한다. 필요하면 별도 화면.
6. **규모를 뽑는다.** PRD에 수치가 있으면(항목 N개, 기간 M주) **그 상한값으로 화면을 채워 본다.** 상한에서 무너지면 화면 구조가 틀린 것이다. 이 상한이 2단계 더미 데이터의 규모가 된다.
7. **상한**: 주 화면 8~12장 + 상태 프레임(빈 / 로딩 / 오류 / **그 도메인 고유의 예외 상태**). 이보다 많으면 2·3번에서 과분할한 것이다. `agent_flow_candidates_max` 안에서 후보를 낸다.

도출한 목록은 **화면 이름과 그 화면이 충족하는 PRD 요구사항 번호를 짝지어** 표로 만든다. 번호가 안 붙는 화면은 없어야 하고, 어느 화면에도 안 붙는 요구사항 번호도 없어야 한다(2단계 종료조건이 이 표를 대조한다).

## 2. PRD 반박 트리거 4개

PRD는 문제 정의이지 설계안이 아니다. 아래에 하나라도 걸리면 반박 대상이다.

| 트리거 | 뜻 |
|---|---|
| **기능 ↔ 상황 어긋남** | PRD의 기능 요구사항과 PRD가 서술한 사용자 상황이 서로 맞지 않는다 |
| **규모에서 무너짐** | 요구사항대로 만들면 PRD가 명시한 규모(항목 수·기간·빈도)에서 화면이 무너진다 |
| **최빈 상태 미처리** | 요구사항이 사용자가 가장 자주 마주치는 상태를 다루지 않는다 |
| **동시 만족 불가** | 서로 다른 요구사항 둘이 같은 화면에서 동시에 만족될 수 없다 |

우리 유형 태그(`문제`/`누락`/`과잉`)와 함께 쓴다. 트리거는 "왜 반박인가", 유형은 "무엇을 바꾸자는 것인가"다.

## 3. 반박 절차

1. **무엇이 충돌하는지** 한 문장. PRD의 어느 대목과 어느 대목인지 **원문 인용**.
2. **대안을 2개** 제시한다. 하나는 PRD를 최대한 지키는 안, 하나는 요구사항을 바꾸는 안.
3. **사용자에게 물을 쉬운 말** 한 문장 — 디자인 용어 없이 상황 예시로. ("PRD에는 X라고 되어 있는데, 실제로 쓰다 보면 Y한 상황이 생길 것 같아요. 그럴 때 Z처럼 되는 게 나을까요, PRD대로가 나을까요?")
4. 사용자가 고른다. 하네스가 임의로 PRD를 무시하지 않는다. 결정을 brief §10 에 남긴다.

**반박은 상한 안에서 가장 큰 충돌부터.** full ≤`agent_prd_pushback_max`(10), fast ≤4이되 실제로 묻는 것은 1~2개. 전부 걸고 넘어지면 반박이 아니라 회피다.

## 4. 실측 예 (형식 참고 — 내용은 다른 도메인)

반려동물 복약 PRD의 "오늘 복약 체크" 요구는 **"안 줬다"와 "줬는데 체크를 안 했다"를 구분하지 못해** 유저스토리 1(중복 투약 위험)을 오히려 유발한다 → 트리거 "동시 만족 불가" → 대안 A: 체크박스 유지 + 확인 단계 / 대안 B: 체크박스를 "내가 줬어요" 기록 행위로 변경 → 사용자 선택 B.

# 인터뷰 프롬프트 원문과 질문 뼈대

> 출처: harness-redesign 스킬의 D1 단계(비전문가 오너 인터뷰 실측, 2026-08-31 라이브). 원문은 요약하지 않고 그대로 쓴다.
> 요약하면 조건절이 빠지고, 빠진 조건절이 정확히 함정이 됐던 것이 실측이다.
> 대상은 **디자인 비전문가 사용자**다. 디자이너가 아니다.

## 1. 질문 품질 규칙 (이게 본체다)

원문:
> "인터뷰할 때는 내가 잘 모를 만한 어휘나 개념 같은 거를 쓰면서 괜히 구체적인 답변을 이끌어내다가 이도 저도 아닌 답변을 듣기보다는, 비전문가여도 잘 대답할 수 있는 적절한 질문들로 잘 구성해서 인터뷰를 해야 돼."

운영 규칙으로 번역:

1. **디자인 어휘 금지.** 위계·밀도·톤앤매너·그리드·컴포넌트·모던·미니멀 같은 단어를 질문에 쓰지 않는다. 쓰려면 체험으로 바꾼다("글자가 많이 들어간 화면과 적게 들어간 화면 중…" 이 아니라 두 화면을 **보여 준다**).
2. **라벨형 질문 금지.** "모던한 게 좋으세요, 클래시컬한 게 좋으세요?" 는 사용자와 하네스의 어휘 이해가 다르면 무의미하다. 대신 구체물을 보여 주고 좋다/싫다+왜.
3. **다이어그램 금지.** IA·플로우를 박스+화살표로 보여 주지 않는다. 그것도 전문 표기법이다. 시나리오 내러티브("아침에 일어나서 앱을 켰다고 해 봅시다…")로 체험시킨다.
4. **"모르겠음" 은 1급 옵션.** 모든 선택형 질문에 넣는다. 눌리면 질문이 나쁜 것이지 사용자가 나쁜 것이 아니다. 1회 재작성, 2회차에도 눌리면 폐기.
5. **한 질문에 한 가지만.** "A 와 B 중 어느 게 좋고 왜 그런가요, 그리고 C 는요" 금지.
6. **되묻기는 "어느 부분이"** 하나로 통일. 사용자가 "토스 같은 느낌" 이라고 하면 "토스의 어느 부분이 그런가요? 화면 하나를 떠올려 보시면" 으로. 이것이 요소 차용(element)과 전체 스타일 차용(whole_style)을 가른다.

## 2. 시작 안내 원문 (역할 분담 선언)

원문(오너의 문제 진술):
> "디자인 개선을 진짜 잘 해 내려면은 지금 뭐가 문제인지부터 파악을 해야 돼. 그래서 이 문제를 비전문가인 나로부터 명확하게 파악해 내기 위해서 네가 적절히 나를 인터뷰해야 돼."

우리 버전(그린필드·PRD 입력): 시작 안내에서 세 가지를 선언한다.
- 사용자는 **반응**만 한다. 기준을 만드는 것은 하네스.
- 디자인 용어를 몰라도 된다. 모르면 "모르겠음".
- 사용자가 자료를 찾아오거나 정리하는 일은 **없다**. 보여 줄 것은 하네스가 만들어 온다.

원문(세션 이탈 거부):
> "나는 지금 이 대화 세션을 벗어나지 않고 싶거든. 그래서 뭔가 내가 판단해야 되는 게 있으면 네가 전부 근거 자료를 주거나 아니면 스크린샷 같은 것을 보내 주던가 해야 돼."

→ 사용자에게 "레퍼런스 앱 스크린샷을 찍어다 주세요" 라고 시키는 순간 이 하네스는 실패다.

## 3. 마무리 조건 원문

> "네가 추론에서 채울 수 있는 부분은 채우고, 이게 충분히 명확해졌다고 판단될 때 다음으로 넘어가면 될까?"

→ 채운 추론은 **전부 가정 로그**로 남긴다. 침묵 처리 금지.

## 4. 원문 보존 원문

> "내가 답변한 내용들도 원문 그대로 어딘가에 남겨 놓아야 추후에 참조해서 이 맥락을 재현하는 데 도움이 될 것 같네"

→ 답변 1건마다 `design/interview_raw.md` 에 즉시 append. 요약본을 따로 만들지 않는다(brief.md 가 요약 역할).

## 5. 결정권 이양 원문 (사용자가 "네가 정해" 라고 할 때)

> "내 의견이 이렇긴 한데 참고만 하고 네가 전문가로서 결정해 줘. 비판적으로 생각해 봐 줘."

> "나는 비전문가야. 그건 전문가인 네가 정해야지. 다만 비전문가 대표인 나의 방향성이나 취향이 필요하다면 그럴 때 적절한 수준으로 요청은 가능해."

→ 사용자가 이렇게 말하면 그 항목은 **하네스가 결정하고 가정 로그에 "사용자 위임" 으로 기록**한다. 되묻지 않는다.

## 6. 질문 뼈대 (≤12, PRD 에 맞게 문구를 바꾼다 — 뼈대만 고정)

각 질문은 "무엇을 캐내는가" 가 정해져 있다. 문구는 PRD 도메인 언어로 바꿔 쓴다. 번호는 순서가 아니라 종류다. 0-A 분석에서 이미 답이 나온 것은 건너뛴다.

| # | 캐내는 것 | 질문 형태 | 기록 태그 |
|---|---|---|---|
| Q1 | 사용 순간의 감정·상황 | "이 앱을 켜는 순간을 하나 떠올려 보세요. 어디서, 어떤 기분으로 켜나요?" (서술) | 무드 축 진술 |
| Q2 | 1등 정보 | "그 순간 화면에서 **딱 하나만** 보인다면 무엇이어야 하나요?" 화면별로 | §2 1등 정보 |
| Q3 | 밀도 진술(간접) | "한 화면에 여러 개가 한꺼번에 보이는 게 편한가요, 하나씩 차례로 보이는 게 편한가요? 예를 들면 …" (선택+모르겠음) | 밀도 축 진술 |
| Q4 | 좋아하는 서비스 + 어느 부분 | "자주 쓰는 앱 중 '이건 쓰기 편하다' 싶은 게 있나요? **어느 화면의 어느 부분이** 그런가요?" | borrow_scope |
| Q5 | 싫어하는 것 | "반대로 '이건 정말 불편하다/보기 싫다' 싶었던 화면이 있나요? 어떤 점이?" | 금지 목록 후보 |
| Q6 | 하드 제약 | "꼭 지켜야 하는 색·로고·글꼴이 있나요? 큰 글씨·고대비가 필요한 사용자가 있나요?" | `[CONSTRAINT]` |
| Q7 | 사용자층 | "이걸 함께 쓸 사람들은 대략 어떤 분들인가요? (연령·기기·익숙함)" | 가정 검증 |
| Q8 | IA 확정 | 시나리오 내러티브 1 읽어 주고 "이 흐름이 맞나요? 어디가 다른가요?" | §2 IA |
| Q9 | IA 확정 2 | 시나리오 2 (까다로운 상황 포함) | §2 IA |
| Q10 | 상태·엣지 | "아무것도 등록 안 된 첫 화면에서 무엇이 보이면 좋겠어요?" / "답이 늦는 사람은 화면에서 어떻게 보이면 좋겠어요?" | 엣지케이스 |
| Q11 | **PRD 반박 확인** | 0-A §6 반박 항목을 상황 예시로 묻는다. 예: "PRD 에는 X 라고 되어 있는데, 실제로 쓰다 보면 Y 한 상황이 생길 것 같아요. 그럴 때 Z 처럼 되는 게 나을까요, PRD 대로가 나을까요?" (선택+모르겠음) | `[PRD-PUSHBACK]` → brief §10 |
| Q11b | 미확정 사항 | 0-A §5 중 디자인 영향 큰 것 1개 (fast 에서는 생략) | 가정 로그 |
| Q12 | 위임 범위 | "여기까지 말씀하신 것 외에는 제가 정해도 될까요? 꼭 직접 고르고 싶은 게 있나요?" | 결정권 |

### fast 모드 질문 세트 (≤6)

Q1 감정·상황 → Q2 1등 정보 → Q6 하드 제약 → Q8 시나리오 1개 → Q11 PRD 반박 1~2개 → Q12 위임. 나머지는 갤러리·월드컵 반응과 가정으로 채운다.

## 7. 갤러리·월드컵 지시문

갤러리:
> "각 번호에 대해 좋다 / 싫다 / 애매 중 하나와, 왜 그런지 한 줄만 적어 주세요. 전부 하지 않아도 됩니다. 눈에 띄는 것부터. 글자 내용이 아니라 보이는 느낌만 봐 주세요."

월드컵(대비쌍):
> "왼쪽과 오른쪽 중 어느 쪽이 더 편한가요? 둘 다 아니어도 됩니다. 왜 그런지 한 줄."

원문 근거(대비쌍이 필요한 이유):
> "색감이 지금 옅은가 진한가는 사실 하나만 보고 잘 모르거든요. 옅은 거랑 진한 거 둘 다 보여 줘야 아는데"

## 8. 규칙 전량표 ack 지시문

> "제가 정리한 기준입니다. 제 말을 잘못 이해한 것이 있으면 번호를 알려 주세요. 없으면 '없음' 이라고 해 주세요."

원문 근거(영속화는 사람이 결정):
> "영속화될 내용을 정확하게 포함해서 브리핑해 줘 봐. 반영하지는 말고."

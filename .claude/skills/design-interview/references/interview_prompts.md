# 인터뷰 프롬프트 원문과 질문 뼈대

> 출처: harness-redesign 스킬의 D1 단계(비전문가 오너 인터뷰 실측, 2026-08-31 라이브). 원문은 요약하지 않고 그대로 쓴다.
> 요약하면 조건절이 빠지고, 빠진 조건절이 정확히 함정이 됐던 것이 실측이다.
> 대상은 **디자인 비전문가 사용자**다. 디자이너가 아니다.
> **§6 이 질문 세트의 유일한 정본이다.** design-harness SKILL 예산표·design-interview SKILL·templates/state.json 상한은 값을 복제하지 않고 이 절을 참조한다. `scripts/check-interview-page.js` P-10·P-13 이 페이지의 `skeleton`·`payload` 를 §6 표와 대조한다.

## 1. 질문 품질 규칙 (이게 본체다)

원문:
> "인터뷰할 때는 내가 잘 모를 만한 어휘나 개념 같은 거를 쓰면서 괜히 구체적인 답변을 이끌어내다가 이도 저도 아닌 답변을 듣기보다는, 비전문가여도 잘 대답할 수 있는 적절한 질문들로 잘 구성해서 인터뷰를 해야 돼."

운영 규칙으로 번역:

1. **디자인 어휘 금지.** 위계·밀도·톤앤매너·그리드·컴포넌트·모던·미니멀 같은 단어를 질문에 쓰지 않는다. 쓰려면 체험으로 바꾼다("글자가 많이 들어간 화면과 적게 들어간 화면 중…" 이 아니라 두 화면을 **보여 준다**).
2. **라벨형 질문 금지.** "모던한 게 좋으세요, 클래시컬한 게 좋으세요?" 는 사용자와 하네스의 어휘 이해가 다르면 무의미하다. 대신 구체물을 보여 주고 좋다/싫다+왜.
3. **다이어그램 금지.** IA·플로우를 박스+화살표로 보여 주지 않는다. 그것도 전문 표기법이다. 시나리오 내러티브("아침에 일어나서 앱을 켰다고 해 봅시다…")로 체험시킨다. 시각 자료가 필요하면 '따라가 보기' 투어(인터뷰 페이지 `flows[]` — 한 번에 장면 하나, 누를 곳 하나)로 보인다. 화면 조각을 가로로 늘어놓는 것도 전문 표기법이라 하지 않는다.
4. **"모르겠음" 은 1급 옵션.** 모든 선택형 질문에 넣는다(`unknown: true`). 눌리면 질문이 나쁜 것이지 사용자가 나쁜 것이 아니다. 재작성·폐기 절차는 design-interview SKILL 0-E(check-brief B-25 의 `[UNCLEAR]` 비율 — 걸린 질문만 장면을 바꿔 1회 재생성, 2회차에도 눌리면 폐기 + §6 '질문 실패') 참조. 페이지 안에서는 되묻지 않는다.
5. **한 질문에 한 가지만.** "A 와 B 중 어느 게 좋고 왜 그런가요, 그리고 C 는요" 금지.
6. **금지어 목록** — 26개(`scripts/lib/forbidden-words.js` 정본, 아래는 사람용 사본). 질문에 아래 단어가 들어가면 그 질문은 폐기하고 상황 질문으로 바꾼다. 디자인 어휘 14: 정보 밀도 · 위계 · 톤앤매너 · 그리드 · 여백 · 대비 · 무드 · 컨셉 · 미니멀 · 모던 · 레이아웃 · 컴포넌트 · 플로우 · IA. 문서·내부 용어 12(§1-11): PRD · 요구사항 · 기획서 · 명세 · 스펙 · 유저 스토리 · 와이어프레임 · 프로토타입 · 온보딩 · UX · UI · 인터페이스. 검사는 `node scripts/lib/forbidden-words.js <파일>` 로 한다 — 사람이 세지 않는다.
7. **선택지는 라벨이 아니라 장면으로 쓴다.** "A안/B안"이 아니라 "화면을 열면 전부 한 번에 보이고 스크롤이 길어요" / "한 번에 하나씩 보이고 다음을 눌러 넘어가요"처럼 사용자가 그 장면을 상상할 수 있게. 선택지는 2~3개(`scene` ≥8자).
8. **취향 말고 상황을 묻는다.** "어떤 느낌이 좋으세요?"(나쁨) → "이걸 언제 어디서 쓰게 되나요?"(좋음).
9. **되묻기는 "어느 부분이"** 하나로 통일. 사용자가 "토스 같은 느낌" 이라고 하면 "토스의 어느 부분이 그런가요? 화면 하나를 떠올려 보시면" 으로. 이것이 요소 차용(element)과 전체 스타일 차용(whole_style)을 가른다.
10. **열린 결정 질문 금지.** "무엇을 넣을까요 / 몇 개가 좋을까요 / 어떻게 보이면 좋을까요" 형은 폐기한다 — 비전문가에게 설계를 시키는 질문이다. 하네스가 의견을 가진 항목(PRD 반박·상태 순위·빈 상태 문구·화면 유무)은 **"저는 X 가 맞다고 봅니다 — 이유. 그래도 Y 가 필요한 상황이 있을까요?"** 형으로 추천을 문장 안에 먼저 밝히고, 선택지는 X / Y / 모르겠음. 의견이 없는 항목은 묻지 않고 장면(갤러리·대비쌍)으로 반응을 받는다. 취향형(토큰 세트·열린 축·초안 승인)은 이 규칙의 예외 — 앵커링을 막기 위해 선택 기록 후 추천을 공개한다.
11. **문서·내부 용어를 사용자 문장에 쓰지 않는다.** 비전공자는 PRD 가 무엇인지 모른다. 하네스 안(brief·state·검사 파일)에서는 쓰되, 사용자에게 보이는 문장(질문·선택지·힌트·되묻기·다이제스트·브리핑)에서는 **PRD → '지금 계획'**, **PRD대로 → '계획대로'**, 요구사항·스펙 → '적혀 있는 것', 온보딩 → '처음 들어왔을 때', UI/UX → '화면/쓰기 편함' 으로 바꿔 말한다. `forbidden-words.js` 의 DOC_WORDS 12개가 정본이고 P-4·B-19·H-13·D-5 가 같은 정본으로 잡는다. 사람이 세지 않는다.
12. **핵심 답은 두 번째 각도로 한 번 더 확인한다(재검증).** Q5(실수의 대가)는 화면 전체를 결정하므로 같은 payload 를 다른 장면(구체 상황 하나: "마감이 지났는데 두 사람이 답이 없어요. 화면이 맨 먼저 보여 줘야 하는 건?")으로 1회 더 묻는다. 페이지 JSON 은 `verifies: <원 질문 id>` 를 싣고(P-10 이 같은 payload 를 이 경우에만 허용), 두 답이 어긋나면 반응이 정본이므로 **두 번째(구체 장면) 답을 우선**하고 0-E 되묻기 F-n 1회로 확인한다. fast 는 Q5 만, full 은 Q5·Q2 까지. 질문 상한에 포함된다.
13. **질문마다 "이걸 정하면 ○○가 달라집니다" 한 줄을 붙인다**(페이지 `effect`, P-15). 왜 묻는지 모르면 대충 답한다(team-3 인터뷰 규칙에서 가져옴). 달라지는 것은 화면의 구체적 부분(글자 크기·맨 위에 놓이는 것·버튼)으로 쓴다.
14. **결정형 질문은 추천을 미리 표시하고, '추천대로' 를 답으로 받는다.** §1-10 의 결정형(Q2 1등 정보 · Q10 빈 상태 · Q11 반박 · Q4' 패턴 · 화면 유무)은 `recommended`·`why` 를 싣고 페이지가 배지로 보인다. 사용자가 '아직 안 고른 질문은 추천대로' 를 누르면 그 값이 `accepted_recommended` 로 저장된다 — **직접 답한 것과 섞지 않고** raw `[ACCEPTED]`, §6 '추천 수락' 행, 0-H 다이제스트 둘째 묶음으로 구분한다(평가 기준 I-3: 추천 수락은 답이 아니라 위임이다). 취향형(Q1·Q5·Q3 계열·갤러리·대비쌍)에는 추천을 미리 보이지 않는다.

## 2. 시작 안내 원문 (역할 분담 선언)

원문(오너의 문제 진술):
> "디자인 개선을 진짜 잘 해 내려면은 지금 뭐가 문제인지부터 파악을 해야 돼. 그래서 이 문제를 비전문가인 나로부터 명확하게 파악해 내기 위해서 네가 적절히 나를 인터뷰해야 돼."

우리 버전(그린필드·PRD 입력): 시작 안내에서 세 가지를 선언한다.
- 사용자는 **반응**만 한다. 기준을 만드는 것은 하네스.
- 디자인 용어를 몰라도 된다. 모르면 "모르겠음".
- 사용자가 자료를 찾아오거나 정리하는 일은 **없다**. 보여 줄 것은 하네스가 만들어 온다.

(인터뷰 페이지에서 이 두 문장 — '디자인 용어를 몰라도 됩니다. 모르면 모르겠음' / '전부 하지 않아도 됩니다. 눈에 띄는 것부터' — 은 템플릿 마크업에 고정돼 있다. maker 의 `intro`·`banner` 에 되풀이하지 않는다.)

원문(세션 이탈 거부):
> "나는 지금 이 대화 세션을 벗어나지 않고 싶거든. 그래서 뭔가 내가 판단해야 되는 게 있으면 네가 전부 근거 자료를 주거나 아니면 스크린샷 같은 것을 보내 주던가 해야 돼."

→ 사용자에게 "레퍼런스 앱 스크린샷을 찍어다 주세요" 라고 시키는 순간 이 하네스는 실패다.
→ 레퍼런스는 하네스가 수집해 장면으로 보여 준다(design-interview SKILL 0-A2 → `design/references.md` → §6 `Q4'` kind: pattern). 금지되는 것은 사용자에게 찾아오게 하는 것이지 레퍼런스 자체가 아니다 — 위 원문 "네가 전부 근거 자료를 주거나" 가 하네스 측 수집을 요구하는 문장이다. 레퍼런스에서 가져오는 것은 패턴(같은 과업을 어떻게 푸는가)뿐이고 색·간격·서체 같은 값은 사용자 반응에서만 온다. 페이지에는 서비스명을 숨긴다.

## 3. 마무리 조건 원문

> "네가 추론에서 채울 수 있는 부분은 채우고, 이게 충분히 명확해졌다고 판단될 때 다음으로 넘어가면 될까?"

→ 채운 추론은 **전부 가정 로그**로 남긴다. 침묵 처리 금지.

## 4. 원문 보존 원문

> "내가 답변한 내용들도 원문 그대로 어딘가에 남겨 놓아야 추후에 참조해서 이 맥락을 재현하는 데 도움이 될 것 같네"

→ 답변 1건마다 `design/interview_raw.md` 에 즉시 append. 요약본을 따로 만들지 않는다(brief.md 가 요약 역할).

## 5. 결정권 이양 원문 (사용자가 "네가 정해" 라고 할 때)

> "내 의견이 이렇긴 한데 참고만 하고 네가 전문가로서 결정해 줘. 비판적으로 생각해 봐 줘."

> "나는 비전문가야. 그건 전문가인 네가 정해야지. 다만 비전문가 대표인 나의 방향성이나 취향이 필요하다면 그럴 때 적절한 수준으로 요청은 가능해."

→ 사용자가 이렇게 말하면 그 항목은 **하네스가 결정하고 가정 로그에 "사용자 위임" 으로 기록**한다(state `human_gates.delegations[]` kind `q12`). 되묻지 않는다.

## 6. 질문 뼈대 (정본 — full 상한 12 / fast 상한 10, PRD 에 맞게 문구를 바꾼다 — 뼈대만 고정)

각 질문은 "무엇을 캐내는가" 와 "그 답이 어디로 흘러가는가(payload → 소비처)" 가 정해져 있다. 문구는 PRD 도메인 언어로 바꿔 쓴다. 번호는 순서가 아니라 종류다. 0-A 분석에서 이미 답이 나온 것은 확인형("맞아요/아니에요")으로 줄이고, 그래도 상한을 넘으면 건너뛰되 `gallery_index.json.skipped[]` 에 'PRD 가 답함: <원문>' 을 남긴다(P-11).

**표 위 규칙**
- **질문 1개 = 소비처 1개 이상.** 소비처를 못 쓰는 질문은 만들지 않는다.
- **같은 payload 두 질문이면 하나 삭제.** 예외는 항목형 payload 둘 — `pushback`(반박 항목마다 1개)·`pattern`(references.md 과업마다 1개). 나머지 payload 는 페이지에 1개만.
- 페이지의 `questions[].skeleton` 은 이 표의 `#` 값, `payload` 는 `payload` 열 값을 그대로 쓴다. 표에 없는 값은 P-10 FAIL.
- 상한은 페이지 항목 수 기준(state `caps.human_interview_questions_max` 12 / `caps_fast` 10). 검증 3 실측: 19항목 3분 31초·타이핑 0줄 — 항목 수가 아니라 타이핑 요구가 피로다.

| # | 캐내는 것 | 질문 형태 | payload | 이 답이 없으면 막히는 것(소비처) | 기록 태그 |
|---|---|---|---|---|---|
| Q1 | 사용 순간의 감정·상황 | "이 앱을 켜는 순간을 하나 떠올려 보세요. 어디서, 어떤 기분으로 켜나요?" (장면 2~3 + 모르겠음 + 자유서술) | `mood_axis` | §3 무드 축 진술 · 0-B 갤러리 감정 키워드(`agent_emotion_keywords_max`) — 없으면 무드 축은 반응만 | 무드 축 진술 |
| Q2 | 1등 정보 (**결정형**, §1-14) | 하네스 추천을 먼저: "앱을 열자마자 **딱 하나만** 보인다면요. 저는 '<0-A 1등 정보 후보 1위>' 가 먼저 보여야 한다고 봅니다 — <이유: 지금 할 일을 정해 주니까요>. 그래도 더 급한 게 있을까요?" 선택지는 0-A 후보 2~3개(장면) + 모르겠음, `recommended`(1위 후보)·`why` 필수 | `top_info` | §2 '이 화면의 1등 정보' 열(B-3b 공백 0) · c_report `top_info` 대조 — 없으면 §2 표를 하네스 가설로 채우고 §6 기록 | §2 1등 정보 |

### fast 모드 질문 세트 (유일한 정본 — 상한 10 = `caps_fast.human_interview_questions_max`)

정본 순서: `Q1` → `Q5` → `Q2` → `Q5`(재검증 1, `verifies`, §1-12) → `Q4'`(kind: pattern ≤2, references.md 있을 때; '레퍼런스 없음' 이면 `Q4` 축약형 1개) → `Q6` → `Q7'`(확인형) → `Q8` → `Q11`(누락 1 + 문제 1, 추천 포함) → `Q12`.

- PRD 가 답한 것은 확인형("맞아요/아니에요")으로 줄인다 — 삭제가 아니다. 확인형도 항목 1개로 센다.
- fast 필수 payload: `mood_axis`·`state_priority`·`top_info`·`constraint`·`ia`·`pushback`·`delegation`·`audience`(P-11). 이 중 빠진 것은 `gallery_index.json.skipped[]` 에 'PRD 가 답함: <원문>' 이 있어야 한다.
- 항목 수: 9종을 다 넣으면 pattern 2 + Q11 2 + Q5 재검증 1 로 12 가 된다. 상한 10 에 걸리면 **pattern 을 1개로, 그래도 넘치면 Q11 문제형을 뺀다**. Q5 재검증·Q11 누락형·Q12 는 줄이지 않는다.
- 나머지 축(밀도·형태·타이포·강조·채도)은 갤러리·`always` 대비쌍 반응과 가정으로 채운다. Q3·Q3b·Q3c·Q4·Q5b·Q6a·Q7·Q9·Q10·Q11b 는 fast 에 넣지 않는다.

### full 모드

표의 모든 뼈대가 후보다(Q3b·Q3c 포함). 상한 12(`caps.human_interview_questions_max`) 안에서 fast 세트를 먼저 채우고, 남는 자리에 Q3 → Q10 → Q3b → Q3c → Q6a → Q4 → Q5b → Q7(Q7' 대신) → Q11b → Q9(flows FL-2) 순으로 더한다. Q7 과 Q7' 는 같은 페이지에 두지 않는다.

## 7. 갤러리·월드컵 지시문

갤러리:
> "각 번호에 대해 좋다 / 싫다 / 애매 중 하나와, 왜 그런지 한 줄만 적어 주세요. 전부 하지 않아도 됩니다. 눈에 띄는 것부터. 글자 내용이 아니라 보이는 느낌만 봐 주세요."

월드컵(대비쌍):
> "왼쪽과 오른쪽 중 어느 쪽이 더 편한가요? 둘 다 아니어도 됩니다. 왜 그런지 한 줄."

원문 근거(대비쌍이 필요한 이유):
> "색감이 지금 옅은가 진한가는 사실 하나만 보고 잘 모르거든요. 옅은 거랑 진한 거 둘 다 보여 줘야 아는데"

진술형 질문이 없는 축(fast: 밀도·형태·타이포·강조·채도 / full: 타이포·채도 + 건너뛴 축)은 `pairs[]` 에 `always: true` 로 넣어 갤러리 결과와 무관하게 항상 묻는다 — 그 축의 두 번째 각도다(rule_schema '진술 0건' 행).

## 8. 규칙 전량표 ack 지시문

> "제가 정리한 기준입니다. 제 말을 잘못 이해한 것이 있으면 번호를 알려 주세요. 없으면 '없음' 이라고 해 주세요."

원문 근거(영속화는 사람이 결정):
> "영속화될 내용을 정확하게 포함해서 브리핑해 줘 봐. 반영하지는 말고."

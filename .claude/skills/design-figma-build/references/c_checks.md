# C단계 — 미적·게슈탈트 판정 기준

> 출처 두 갈래를 합쳤다. 팀 디자이너 A(design-harness 브랜치)의 **수치가 있는 C-1~C-8**과 팀 디자이너 B(noyunseo 브랜치)의 **"1차 목적 선언 → 판정"** 및 **긍정형 매력 판정**. 두 분의 입장이 갈리는 지점(수치 고정 여부)은 이렇게 정리했다: **목적을 먼저 선언하고, 수치는 프로젝트 규칙(design.md §4C)이 덮어쓸 수 있는 기본값으로 쓴다.** C-10 은 하네스 실측(1등 정보가 1차 인상과 어긋난 화면)에서 추가했다.
> 판정자(`design-judge` 2콜)는 이 파일과 design.md·스크린샷(Figma 캡처 + 2-H 승인 시점의 초안 렌더 `design/verify/draft_shots/*.png` — **비교 대상**)만 본다. **decisions.md 의 선택 이유·제작자 의도는 판정 근거가 아니다** — 브리프에 넣지 않는다. 초안 렌더는 "무엇이 승인됐는가" 의 사실이지 의도 설명이 아니다.
> 이 파일에 없는 것은 **취향의 값**(색·간격·서체)이다. 값은 사용자 반응(design.md §4C·§6)에서, 같은 과업을 실제 서비스가 어떻게 푸는가(패턴)는 0-A2 레퍼런스에서, 바닥선(접근성·규격·슬롭 패턴)은 이 파일과 design.md §3 에서 온다. 이 파일에 근거한 판정은 취향 발명이 아니다.

**전제**: 스크린샷을 **Read 로 직접 열어** 판정한다. 노드 속성이나 소스로 대체할 수 없다. 스크린샷을 못 얻었으면 결과는 통과가 아니라 `C_NOT_RUN` 이다.
**판정 원칙**: 두 사람이 같은 화면을 보고 같은 결론에 도달할 수 있어야 한다. "위계가 약하다"는 판정이 아니다. **어느 요소가 / 어떤 수치로 / 어느 기준을** 어겼는지 쓴다.
**결과의 형식**: 화면마다 `c_report.json` 의 `checks[]`(C-n · SLOP-SWEEP · POS-<키>) · `positive`(§2 의 7키 boolean) · `tasks[]` · `score` · `top_info` · `fidelity` 를 채운다. `check-c-report.js` CR-1~CR-12 가 이것을 센다 — 빈 칸은 판정 안 함으로 계산된다.

## 0. 먼저 이 화면의 1차 목적을 선언한다 (필수)

목적을 적지 않고 판정하지 않는다. 같은 화면이 목적에 따라 통과도 되고 실패도 된다. 목적은 design.md §7 핵심 과업과 §5 화면별 1등 정보(brief §2 화면표의 사본)에서 읽는다.

| 1차 목적 | 통과 조건 | 이 목적에서의 실패 |
|---|---|---|
| **빠른 처리형** — 한 손, 몇 초, 반복 사용 | 3초 안에 다음 행동이 잡힌다 | 안 잡히면 실패. **장식 요소가 있으면 그 자체로 실패. 히어로 영역 불필요** |
| **현황 파악형** — 전체를 훑고 판단 | 전체 상태가 한눈에 잡힌다 | 안 잡히면 실패. **비교가 필요한 숫자가 글자로만 나열돼 있으면 실패** |
| **선택형** — 후보 중 고르기 | 선택지 간 차이가 보인다 | 차이가 시각적으로 드러나지 않으면 실패 |
| **입력형** — 값을 넣기 | 입력 순서가 자연스럽다 | 순서가 부자연스러우면 실패. **히어로 영역 불필요** |

- 한 화면에 목적이 둘 이상으로 보이면 화면을 쪼개야 한다는 신호 → `direction` 분류.
- **목적을 도중에 바꾸면 그 화면의 모든 판정이 바뀐다.** 목적 변경은 brief 에 사용자 답 원문·이유·포기한 것을 기록한 뒤에만 유효하다. 근거 없이 목적이 바뀌면 그 이후 판정은 무효 — "빠른 처리형인데 히어로를 넣고 싶어져서 현황 파악형이라 부르기 시작하는" 일이 여기서 일어난다.

## 1. 부정형 기준 — 기본 수치 (design.md §4C 가 덮어쓸 수 있다)

### C-1. 섹션 간 색온도·조명 일관성
**판정**: 배경 톤의 hue 가 섹션 간 **15° 이상** 벌어지면 실패. 순수 회색(채도 0)과 유채색 회색이 한 화면에 섞이면 실패. 그림자 방향·세기가 요소마다 다르면 실패.
**수정**: surface 토큰 하나로 통일. 섹션 구분은 hue 가 아니라 elevation 또는 여백.

### C-2. 시각적 위계
**판정**: 3초 보고 "가장 중요한 것 1개"를 지목할 수 없으면 실패. primary 액션이 **2개 이상** 동등 강도면 실패. 인접 텍스트 두 단계 크기 차이가 **2px 이하**면 실패. 크기·굵기·색을 **동시에 3개** 써서 강조하면 과잉.
**긍정 조건**: 위계는 크기·색·여백 중 **최소 두 가지**로 표현돼야 한다. 하나만 쓰면 강조지 위계가 아니다.
**수정**: typography scale 의 단계 차이로. 임의 크기 생성 금지.

### C-3. 여백 리듬
**판정**: 섹션 간 > 섹션 내부 > 요소 간 순서가 깨지면 실패. 라벨과 그 입력 사이 간격이 그 입력과 다음 그룹 사이 간격보다 크거나 같으면 실패(근접성). 스케일 밖 값(18, 22)이 보이면 그 자체가 실패 신호. **텍스트 블록 여백은 바운딩 박스가 아니라 글자(잉크) 기준**으로 본다.
**수정**: spacing 스케일 값만. 여백은 정보 그룹의 경계와 일치해야 한다.

### C-4. 정보 밀도
**판정**: 첫 화면(스크롤 전)에 사용자가 결정해야 할 항목이 **5개**를 넘으면 실패. 구분선 3개 이상 연속이면 밀도 초과 신호. 카드 안에 카드 3겹 이상이면 실패. 반대로 화면의 **60% 이상이 빈 여백**이고 콘텐츠가 위쪽에만 몰려 있으면 미완성.

### C-5. 클리셰 / AI 슬롭 — 아래 중 **2개 이상**이면 실패, `direction` 분류
- [ ] 보라→파랑(청록→핑크) 그라디언트 배경
- [ ] 이유 없는 glassmorphism / backdrop-blur
- [ ] 모든 카드가 동일 크기인 3열 그리드
- [ ] "아이콘 + 굵은 제목 + 회색 본문 2줄" 블록 3회 이상 반복
- [ ] 이모지를 아이콘 대용으로 사용
- [ ] 근거 없는 다크모드 기본값
- [ ] 모든 요소에 동일한 그림자(elevation 위계 없음)
- [ ] 채움용 통계 숫자("99.9%", "10,000+")
- [ ] "Lorem ipsum" / "제목을 입력하세요" 잔존
- [ ] 좌측 컬러 보더로 카드 강조 (실측 슬롭)
- [ ] 점선 테두리 · 하트·반지·꽃 같은 도메인 클리셰 장식

C 검출력 시험(figma-build 3-E, full)의 합성 프레임은 이 목록의 4개(그라디언트·이모지·동일 그림자 3열·`#000` 본문은 C-8)를 심어 둔다 — 그 프레임을 여기서 ≥2 로 잡지 못하면 그 라운드의 판정은 무효다.

### C-6. 엣지케이스·필수 화면 실물 완성도 — 아래를 **실제로 렌더해 보지 않았으면 미수행**
- [ ] 빈 상태 — "데이터가 없습니다" 한 줄이면 실패. **다음 행동**이 있어야 한다
- [ ] 최장 문자열 — 한글 기준 2배로 늘렸을 때 잘리거나 깨지지 않는가
- [ ] 로딩 — 로딩 중 버튼 너비가 변하면 실패
- [ ] **오류 상태(`error`) 프레임이 있고**, 무엇이 잘못됐고 무엇을 하면 되는지 **둘 다** 있는가 — 프레임 자체가 없으면 실패(빈 상태로 대체 불가)
- [ ] **사용자가 가장 자주 마주치는 상태**(design.md §5 의 상태 강조 순위 — brief §2d Q5 답의 사본)가 한눈에 보이는가
- [ ] **주 행동이 스크롤 없이 보이는가** — 첫 화면(y ≤ 844) 안에 있거나 하단 고정 바. 잘린 버튼은 실패(실측: 회신 화면 "선택 완료" 잘림). 긴 화면은 전체 높이 캡처로 본다
- [ ] **첫 진입 화면이 존재하고 T-1(design.md §7 첫 과업)이 거기서 시작하는가** — 홈의 빈 상태로 첫 진입을 대체하면 실패. 사용자 역할이 둘 이상(작성자/초대받은 쪽 등)이면 **초대받은 쪽의 첫 화면(링크로 들어온 순간)** 이 없으면 실패
- [ ] 초안 렌더(`draft_shots`)와 같은 상태의 Figma 캡처를 나란히 놓았을 때 요소 구성·순서가 같은가 — 다르면 `fidelity.elements_match=false` 로 기록하고 여기 실패

### C-7. 균일함(AI 슬롭)의 5가지 신호 — 각각 독립 판정
- [ ] **카드 균일** — 한 화면의 카드가 전부 같은 크기·라운드·그림자. 중요도가 다르면 최소 한 속성이 달라야 한다
- [ ] **강조 개수** — 화면당 강조가 0개이거나 3개 이상. 시선이 처음 닿을 곳은 정확히 하나
- [ ] **제목/본문 배율** — 1.5배 미만이면 위계 부재(굵기만 다르면 강조지 위계가 아니다)
- [ ] **시각 요소 부재** — 텍스트 블록만 세로로 쌓이고 아이콘·도형·차트·아바타·막대가 0개
- [ ] **여백 균일** — 전 구간 동일. 섹션 사이는 요소 사이의 2배 이상

### C-8. 시각 교정 기준
- [ ] 굵은 검정 테두리·강한 그림자로 강조를 만들면 실패. 일반 카드는 1px 중성 경계 또는 표면 차이로만
- [ ] 선택 상태를 검정으로 칠하면 실패. 선택은 브랜드 계열 연한 배경 + 진한 테두리/표시
- [ ] 본문·제목에 순수 검정(#000)을 쓰면 실패
- [ ] 서로 다른 의미(충돌·경고·정보·완료·대기)에 같은 색·같은 배지를 쓰면 실패. **색과 아이콘이 함께** 달라야 상태로 읽힌다
- [ ] 아이콘만 있고 텍스트가 없으면 실패. 한 화면에 아이콘·이모지 종류 5개 초과면 실패. 기능(라인)과 장식(컬러) 역할이 섞이면 실패
- [ ] **비활성 탭·아이콘 뒤에 상자(회색 네모)가 보이면 실패.** 아이콘 컨테이너의 남은 fill 이다. 활성 표시는 색 변경 또는 옅은 알약 하나(실측 D-33: 탭 4개 전부 회색 상자 + 활성은 네모 테두리 — 어느 플랫폼 관행에도 없다)

### C-9. 지어내기 금지
가이드에 값이 없는 항목을 그럴듯한 기본값으로 채웠으면 실패. 올바른 처리는 가장 작은 미해결 단위만 생략하고 brief §6 에 가정으로 남기는 것. 침묵 통과와 명시적 가정은 다르다.

### C-10. 1등 정보 일치
**판정**: design.md §5 에 적힌 이 화면의 1등 정보가 **1콜 블라인드의 1순위**(`c_first_impression.json` rank 1)와 다르면 실패. 같은 요소를 다른 말로 불렀는지는 위치·크기로 확인하고, 그래도 다르면 실패다. `c_report.json` `top_info.{declared, blind_first, match, diagnosis}` 에 기록한다(`check-c-report.js` CR-8 이 전 화면 `match=true` 를 센다). 초안 렌더(`draft_shots`)에서 1등 정보가 있던 위치와 Figma 캡처의 위치가 다르면 `fidelity.primary_position_match=false` 로 같이 기록한다.
**빈발 사례**: 빈발 상태 칩 4개가 같은 강도라 상태보다 제목이 먼저 읽힘 / 주 숫자(D-day·인원·금액)와 그 단위·라벨이 같은 크기라 숫자가 먼저 잡히지 않음 / 1등 정보가 접힌 섹션·스크롤 뒤에 있고 첫 화면에는 장식만 있음.
**수정**: 1등 정보에 크기·색·여백 중 **2가지**를 준다(단위는 숫자의 절반 이하, 칩은 빈발 상태 1개만 채움색) → `local`. 화면의 구조가 다른 정보를 먼저 보이도록 짜여 있으면(1등 정보가 다른 섹션 안에 있거나 첫 화면 밖) → `direction`(2-B 재발산).

## 2. 긍정형 매력 판정 — 부정형을 다 통과한 뒤에 적용, **이걸 통과해야 최종 PASS**

부정형만 통과하면 "틀리지 않은 화면"이 나오지 "좋은 화면"이 나오지 않는다. 채점의 1점(AI 슬롭)과 5점(시니어)을 가르는 것이 여기다. 7항목은 `c_report.json` `positive` 의 7키(괄호)로 **전부 boolean** 으로 적는다. `false` 는 그냥 두지 않는다 — `brand_device`·`unique_element` 가 false 인데 design.md §10 의 브랜드 장치 칸이 비어 있으면 `taste_gap`, 그 밖의 false 는 `direction` 으로 `checks[]` 에 `POS-<키>` fail 을 함께 낸다. 사용자 예외 승인(`state.human_gates.final_ack.exceptions[]`) 없는 false 는 종료를 막는다(`check-c-report.js` CR-6).

- [ ] **이 화면에만 있는 것이 하나라도 있는가.** (`unique_element`) 다른 앱에서 그대로 가져와도 어색하지 않다면 실패. 카드 + 배지 + 하단 탭 조합만으로는 어떤 서비스도 되지 못한다. (적합성 축)
- [ ] **가장 중요한 수치가 압도적인가.** (`dominant_number`) 핵심 숫자는 주변 텍스트와 **2배 이상**. 숫자와 단위·라벨을 같은 크기로 쓰면 실패. (현황 파악형에서 필수. 수치가 없는 화면은 1등 정보 요소에 같은 기준을 적용)
- [ ] **정보 종류가 다르면 형태도 다른가.** (`form_differs_by_kind`) 대기 / 완료 / 예외가 **같은 카드 형태**면 실패. 색과 배지만 바꾸고 형태가 같으면 같은 것으로 읽힌다.
- [ ] **표면에 층이 있는가.** (`surface_layers`) 모든 영역이 같은 배경색이면 평면적. 최소 2단계(배경 / 카드 / 강조).
- [ ] **브랜드 장치가 살아 있는가.** (`brand_device`) design.md **§10 표현 전략**의 "이 프로젝트의 장치" 하나가 이 화면에 있는가. 토큰을 그대로 쓴 것은 브랜드 표현이 아니라 규격 준수다. §10 의 장치 칸이 비어 있으면 이 항목은 판정 불가 → false + `taste_gap`.
- [ ] **시각 요소를 넣었다면 "이게 없으면 이해가 느려지는가"** (`visual_elements_justified`) — 아니면 제거 대상. 넣은 것 자체는 점수가 아니다. 시각 요소가 없는 화면은 C-7 '시각 요소 부재' 가 먼저 걸린다.
- [ ] **총괄 — "전문 디자이너의 결과물로 보이는가"를 자문한다.** (`looks_professional`) 아니면 위 항목 중 어디에 걸리는지 지목한다. "그냥 별로"로 끝내지 않는다.

## 3. 채점 3축 매핑과 자체 채점

| 축 | 근거 항목 | `c_report.json` 의 근거 칸 |
|---|---|---|
| UI 심미 | C-1·C-3·**C-5**·C-7·C-8 + 매력 판정 표면(`surface_layers`)·수치(`dominant_number`)·형태(`form_differs_by_kind`) | `checks[]` C-1/C-3/C-5/C-7/C-8, `positive` 3키 |
| UX 직관 | 0 목적 통과 조건 + C-2·C-4·C-6·**C-10** + 핵심 과업 3개 경로 추적(`tasks[]` 찾음/헤맴/불가, 역할별) | `checks[]` C-2/C-4/C-6/C-10, `top_info`, `tasks[]` |

UI 1점의 정의(design-harness: "AI 가 만든 티")는 C-5 에 대응한다 — C-5 가 실패한 화면의 UI 점수는 1 이다.

자체 채점 1·3·5(1 = AI 슬롭처럼 보임, 3 = 신입 디자이너, 5 = 시니어)는 신호이지 최종 게이트가 아니다 — 게이트는 부정형·긍정형 판정이다. 다만 **3 미만인 축은 이유를 FAIL 항목으로 반드시 낸다**: 그 축에 매핑된 검사(위 표) 중 fail 이 하나도 없이 3 미만을 적으면 `check-c-report.js` CR-5 가 FAIL 로 잡는다. 점수는 3-G 에서 사용자에게 쉬운 말(1=AI 가 만든 티, 3=신입, 5=시니어)로 고지된다.

## 5. 카탈로그 갱신 규칙

C단계에서 새로 발견한 실패 유형은 **이 파일에 추가**한다. 형식은 `판정 기준(수치) + 빈발 사례 + 수정 방침` 3종 세트(C-10 이 그 예다). 셋 중 하나라도 없으면 추가하지 않는다. 표본 1건으로 규칙을 늘리지 않는다 — 다른 도메인에서 재현될 때 승격한다. 좋은 예를 늘리는 것보다 탈락 패턴을 늘리는 것이 품질을 올리는 유일한 방법이다.

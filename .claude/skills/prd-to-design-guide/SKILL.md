# prd-to-design-guide

PRD를 읽고 제품의 성격·톤·사용자 맥락에 맞는 디자인 토큰을 도출해,
**사람이 읽는 가이드 문서**와 **Figma 캔버스 시각 정리본**을 동시에 만든다.

`oss-design-harness`의 0단계 산출물을 만드는 스킬이다. 이 스킬의 출력이 이후 모든 게이트의 판단 근거가 된다.

## 작성 계약 — 먼저 읽는다

산출물은 `templates/design-guide.md`(design-md v1) 스키마를 따른다.
준거 예시는 `guide/reference/toss.design.md`다. 아래 4가지가 이 스킬 품질의 전부다.

1. **증거 등급을 붙인다.** 모든 값에 출처를 남긴다: `prd` / `repo` / `client-quote` / `measured` / `assumption` / `extension`.
2. **모르면 비운다.** PRD에 근거가 없는 값을 그럴듯한 기본값으로 채우지 않는다. 해결되지 않은 **가장 작은 단위만** 생략하고 Unknowns에 기록한다. 그림자·모션처럼 근거가 약한 카테고리는 "이 리비전에서 승격된 토큰 없음"이라고 쓰는 것이 정답일 때가 많다.
3. **표면을 섞지 않는다.** 모바일 제품 UI와 마케팅 웹의 지오메트리를 별도 이름으로 유지한다. 서로 다른 두 값을 평균내지 않는다.
4. **없는 것을 지어내지 않는다.** PRD에 없는 컴포넌트를 업계 관행으로 채우지 않는다. 필요하면 `extension`으로 명시한다.

**PRD에 명시적 브랜드 가이드(로고, 지정 색상, 지정 폰트)가 있으면 그것이 최우선이다.**
단, 로고 브랜드 컬러를 UI primary로 조용히 대체하지 않는다 — 둘은 다른 역할이다.

---

## 1단계 — PRD 분석

PRD 파일 또는 붙여넣은 텍스트에서 아래를 추출한다. 추출한 문장은 **원문 인용으로** 남긴다.

- **서비스 정체성**: 서비스명, 한 줄 설명, 핵심 가치
- **타깃 사용자**: 사용자 유형, 연령대, 사용 맥락(모바일/데스크톱, 이동 중/집중)
- **감성 키워드**: 도메인·톤·문화적 맥락에서 3~5개 (예: 따뜻한, 신뢰감, 축제적, 실용적)
- **기능 복잡도**: 핵심 화면 수, 정보 밀도, 상태 종류
- **플랫폼**: 모바일 우선 / 데스크톱 우선 / 반응형

PRD에서 읽히지 않는 항목은 추측하지 말고 사용자에게 묻거나 `assumption`으로 명시한다.

## 2단계 — 디자인 토큰 도출

각 결정에 **"왜 이 값인지"를 PRD 맥락과 연결해** 근거를 적는다. 근거 없는 값은 토큰이 아니다.

### A. 컬러
- **Primary** 1개 + 밝기 변형 (50/100/300/500/700/900)
- **Secondary** 1개 + 3단계
- **Neutral** 최소 7단계 (50~900). 순수 회색과 유채색 회색을 섞지 않는다 — 하나를 고른다
- **Semantic** Success / Warning / Error / Info 각 배경+텍스트 쌍
- **Surface** Background / Surface / Elevated 계층
- 각 색은 HEX + **WCAG AA 대비율 통과 여부** 표기 (본문 4.5:1, 큰 텍스트·비텍스트 3:1)

### B. 타이포그래피
- 본문용 1개 + 필요시 디스플레이용 1개. **한글 서비스면 한글 웹폰트 지원 폰트를 우선**하고, 시스템 폰트 fallback을 함께 명시
- 스케일: Display / H1~H3 / Body Large / Body / Body Small / Caption / Overline
- 각 단계에 size(px), line-height(배수), weight, letter-spacing
- 인접 두 단계의 크기 차이는 **2px 초과**여야 한다. 그 이하는 위계가 아니라 실수로 읽힌다
- 모바일/데스크톱 스케일이 다르면 양쪽 다 표기

### C. 스페이싱
- 기본 단위 4px 또는 8px
- 스케일: 2, 4, 8, 12, 16, 20, 24, 32, 40, 48, 64, 80, 96
- **용도 매핑 필수** (4px=아이콘-텍스트, 16px=섹션 내부 패딩, 32px=섹션 간)
- 근접성 규칙: 라벨-필드 간격 < 그룹 간 간격. 이 관계가 깨지는 값 조합은 채택하지 않는다
- 버튼·카드·인풋·모달의 내부 여백 기본값

### D. 래디어스
- 스케일: none(0), sm(4), md(8), lg(12), xl(16), 2xl(20), full(9999)
- 컴포넌트별 용도 매핑
- 동심원 규칙: `outerRadius = innerRadius + padding`

### E. 그림자 & 엘리베이션
- sm(미묘) / md(카드·드롭다운) / lg(모달·오버레이) 3단계, 각각 offset·blur·spread·color+opacity
- **근거가 약하면 승격하지 않는다.** 모든 요소에 동일 그림자를 균일하게 까는 것은 elevation이 아니다

### F. 아이콘 & 에셋
- 스타일 Outlined / Filled / Duotone 중 택1 + 근거
- 크기 16 / 20 / 24px, 스트로크는 본문 weight에 맞춘다 (Regular 400 → 1.5px)

## 3단계 — 가이드 문서 작성

`templates/design-guide.md`를 프로젝트 폴더로 복사해 7개 섹션을 채운다.
섹션과 `<!-- design-md:section ... -->` 마커는 **고정**이다. 추가·삭제·재배열하지 않는다.

동시에 `templates/project.rules.json`의 `tokens` 블록을 채우고 `status`를 `filled`로 올린다.
`source`에는 근거를 적는다(PRD 인용 또는 `"가정: ..."`).
**`unfilled`인 `blocker`가 남아 있으면 이후 파이프라인이 진입을 거부한다.**

## 4단계 — Figma 캔버스에 시각 정리

> **`use_figma` 호출 전에 반드시 `figma-use` 스킬을 먼저 로드한다.** 새 파일이 필요하면
> `figma-create-new-file` 스킬을 로드한 뒤 `create_new_file`을 호출한다.
> 대안으로 `generate_figma_design`을 쓸 수 있다. `create_design`이라는 툴은 존재하지 않는다.

데스크톱 폭 프레임 하나에 아래 섹션을 세로로 배치한다:

- **헤더** — 서비스명 + "Design Guide" + 감성 키워드 태그 + 생성일
- **컬러 팔레트** — 카테고리별 스워치(사각형 + HEX + 토큰명 + 대비율)
- **타이포 스케일** — 각 단계를 실제 폰트 크기로 렌더해 시각적 계층을 드러낸다
- **스페이싱 스케일** — 각 값을 길이가 다른 바로 시각화 + 용도 라벨
- **래디어스 스케일** — 실제 래디어스가 적용된 사각형
- **엘리베이션** — 각 레벨이 적용된 카드 예시 (승격한 토큰이 있을 때만)
- **적용 예시** — 토큰이 조합된 버튼·카드·인풋 미니 컴포넌트 3~5개, 각각 상태 포함

**시각 원칙**
- 가이드 자체가 도출한 컬러·타이포로 만들어져야 한다 (메타적 일관성). 가이드 문서만 다른 스타일이면 그 가이드는 신뢰받지 못한다
- 각 항목에 토큰명 + 값 + 용도를 함께 표기
- 스캔하기 쉬운 문서형 레이아웃. 장식 금지

## 5단계 — 결정 근거 요약

캔버스 작업 후 채팅으로 간략히 보고한다:

- 왜 이 Primary 컬러인지 — PRD의 도메인/감성과 연결
- 왜 이 폰트인지 — 타깃 사용자의 가독성/접근성 맥락
- 왜 이 스페이싱 체계인지 — 정보 밀도와 플랫폼
- **무엇을 비워뒀는지** — Unknowns 목록과 그 이유. 이 항목을 빠뜨리면 보고가 완결되지 않는다

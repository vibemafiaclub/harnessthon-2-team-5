# Decisions — 청첩장모임 스케줄러

## 식별된 독립 축

1. **계정/워크스페이스 구조** — 예비신랑·예비신부가 하나의 서비스를 같이 쓰는 방식
2. **정보 구조(IA)** — 하단 탭이 무엇을 중심으로 조직되는가
3. **모임 유형 처리** — 1:1 만남을 그룹 모임과 구조적으로 분리할지 여부
4. **응답자(초대받은 지인) 구조** — 응답자도 계정을 갖고 여러 커플 요청을 통합해서 볼지 여부
5. **회신 마감 초과 처리** — 마감이 지나도 응답 안 한 사람이 있을 때 시스템 개입 수준

(축을 나누지 않고 화면 전체를 통째로 비교했다면, 계정구조 결정과 IA 결정이 뒤섞여 사용자가 무엇 때문에 그 선택을 했는지 안 남았을 것)

## 축별 후보·비교·선택

### 축 1: 계정/워크스페이스 구조

| 후보 | 설명 | 비교 근거 | 선택 여부 |
|---|---|---|---|
| A. 하나의 커플 스페이스 + 각자 로그인 | 신랑·신부 각자 계정, 초대 코드로 같은 공간 공유 | 개인화(내 쪽/배우자 쪽 구분)와 공유(통합 뷰)를 동시에 만족 | ✅ |
| B. 계정 1개를 공유 | 한 사람이 가입 후 ID/PW 공유 | 구현 가장 쉬우나 동시 편집·개인화 불가 | |
| C. 완전 독립 계정, 수동 공유 | 각자 따로 쓰다 필요시 이미지/링크로 공유 | PRD의 "둘이 함께 쓴다" 요구와 거리가 멂 | |

**선택 이유**: PRD가 "예비신랑·예비신부 두 사람이 함께 쓰는 것을 전제"라고 명시했고, 동시에 "신랑 쪽 지인 풀과 신부 쪽 지인 풀이 따로 관리되다가도 양가가 같이 나가야 하는 모임이 섞여 있다"고 했으므로 개인화+공유가 동시에 필요.

### 축 2: 정보 구조(IA)

시각적 축이라 브라우저 시각 동반자로 와이어프레임 3안을 병렬 렌더링해 비교.

| 후보 | 설명 | 비교 근거 | 선택 여부 |
|---|---|---|---|
| A. 지인풀 중심 | 지인 목록이 메인, 모임은 사람에서 파생 | 중복 소속 관리는 쉬우나 "오늘 뭘 챙겨야 하나"가 안 보임 | |
| B. 모임 중심 | 하단 탭: 모임(상태별)/전체일정/지인풀. 모임 상태(대기·확정예정·확정·완료)가 메인 | PRD §4-6(진행 상태 구분) 요구사항과 1:1 매칭 | ✅ |
| C. 캘린더 중심 | 월간 캘린더가 메인 | 겹침 확인엔 최적이나 회신 마감 임박 같은 "행동 필요" 항목이 캘린더에 묻힘 | |

**선택 이유**: B를 기본으로 채택하되, C의 장점(겹침 조망)은 전체일정 탭의 캘린더 서브뷰로 흡수. 최종 하단 탭은 홈/모임/전체일정/지인풀 4개로 확정(홈은 B안 승인 후 추가 논의에서 대시보드로 신설).

**확정 화면 인벤토리 (15개)** — 3단계(HTML 프리뷰) 산출물과 1:1 대응, 실제 파일: `docs/wedding-scheduler/preview/index.html`

### 축 3: 모임 유형 처리

| 후보 | 설명 | 비교 근거 | 선택 여부 |
|---|---|---|---|
| A. 같은 "모임" 개념, 구성원 1명 | 별도 타입 없이 구성원 수만 다름 | 데이터 모델 단순, 3명이든 1명이든 같은 편성→조율→확정 플로우 | ✅ |
| B. 1:1을 별도 모임 타입으로 분리 | UI상 "그룹 모임" vs "개별 약속"을 다른 아이콘/색으로 구분 | 구분은 명확해지지만 화면·로직이 늘어남 | |

**선택 이유**: PRD의 "직장 상사처럼 1:1로 따로 만나야 하는 관계도 섞여 있다"는 요구는 구성원 수 1명으로 충분히 표현 가능, 별도 타입 분리는 YAGNI.

### 축 4: 응답자(초대받은 지인) 구조

| 후보 | 설명 | 비교 근거 | 선택 여부 |
|---|---|---|---|
| A. 응답자도 계정 보유, 통합 받은함 | 여러 커플의 요청이 한 리스트에 모임 | PRD 유저스토리 2번("여러 커플로부터 동시에 요청을 받아 한 번에 파악")을 직접 충족 | ✅ |
| B. 응답자는 비회원, 링크로만 개별 응답 | 가입 부담 없음 | 여러 커플 요청을 한곳에서 모아보는 게 구조적으로 불가능 — 유저스토리 2번과 충돌 | |

**선택 이유**: 유저스토리를 문자 그대로 만족시키려면 응답자도 계정 기반 통합 받은함이 필수. 이 결정이 전체 IA에 "받은 초대함" 화면을 홈 진입점으로 추가하게 만든 원인.

### 축 5: 회신 마감 초과 처리

| 후보 | 설명 | 비교 근거 | 선택 여부 |
|---|---|---|---|
| A. 자동 처리 없이 "미회신자 있음" 알림만 | 예비부부가 직접 판단(독촉/마감연장/날짜재제안) | 사람 관계가 얽힌 민감한 문제를 시스템이 임의로 확정·독촉하지 않음 | ✅ |
| B. 마감 지나면 자동 '불참' 처리 | 시스템이 자동 배제하고 다수결로 날짜 확정 진행 | 사람 간 관계를 시스템이 임의로 정리하는 셈이라 조심스러움 | |

**선택 이유**: 청첩장모임이라는 도메인 특수성(관계 관리) — 자동화보다 사람의 최종 판단을 항상 남겨야 함.

## 남은 트레이드오프

- B단계 전체를 하네스(단일 관점) 추천안 제시 + 사용자 승인으로 수렴했다 — 조직 원칙인 "최소 2개 이상 페르소나 교차비평"은 시간 예산상 생략함. 다음 세션에서 최소 2인 페르소나(예: "처음 쓰는 예비신부" / "여러 커플 초대를 동시에 받는 지인") 교차비평을 끼워 넣는 게 TODO로 남음.
- Variant 상태 커버리지(hover/disabled/loading/error)는 정적 HTML 프리뷰 단계에서 다루지 않음 — Figma 컴포넌트 배리언트 단계로 이월.

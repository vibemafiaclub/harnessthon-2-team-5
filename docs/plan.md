# 작업 계획 — 가이드 준수형 와이어프레임→디자인 파이프라인

> `docs/concept.md`가 "무엇을 왜"라면, 이 문서는 "무엇을 어떤 순서로 만드는가"다.
> 컨셉의 4단계 프레임(0/B/A/C)은 그대로 두고, 그 위에 **실행 파이프라인과 게이트**를 얹는다.

## 0. 전제 — 프롬프트는 준수를 보장하지 못한다

"어떠한 상황에서도 디자인 가이드를 준수"라는 요구는 스킬 프롬프트로는 달성할 수 없다.
아무리 강하게 써도 확률적 준수에 그친다. 보장되는 유일한 방법은 **결정론적 게이트** —
검사기가 위반을 잡으면 다음 단계로 넘어가지 못하게 막는 것(fail-closed)이다.

따라서 이 작업의 본질은 "가이드를 잘 지키는 에이전트"가 아니라,
**가이드를 기계가 검사 가능한 형태로 바꾸고 + 통과 못 하면 멈추는 파이프라인**을 만드는 것이다.
에이전트는 그 파이프라인의 부품이지 보증 주체가 아니다.

## 1. 갭 분석

| 필요한 것 | 현재 상태 | 갭 |
|---|---|---|
| 기계가 읽는 디자인 가이드 | `templates/brief.md` — 자유서술 마크다운 | **검증 불가.** "Spacing 그리드: TODO"는 사람만 읽는다 |
| 와이어프레임 단계 | 프레임워크에 없음 | 0→B→A/C만 존재. **W(구조)/D(비주얼) 분리 부재** |
| A단계 검사기 | 체크 카테고리 목록만 존재 | 실행 코드 0줄 |
| 게이트(진행 차단) | 없음 | C 실패 라우팅만 있고 **A 실패 시 거동이 미정의** |
| 에이전트 | 없음 | `.claude/agents/` 디렉터리 자체가 없음 |

가장 큰 갭은 두 번째다. 와이어프레임과 최종 디자인은 지켜야 할 가이드가 서로 다른데
(와이어프레임에서 색온도 일관성을 검사하는 것은 무의미), 현재 프레임워크는 "다 만든 후"를
한 덩어리로 본다. 이 분리가 작업의 절반이다.

## 2. 목표 파이프라인

```
0. 정렬 ──> guide 컴파일 ──┐
                            │ (모든 하위 단계가 이 파일만 참조)
   ┌────────────────────────┘
   ↓
   W. 와이어프레임 생성 ──> [게이트 A-w] ──> [게이트 C-w] ──┐
                              구조 검사        구조 가독성    │ 실패 시 라우팅
   ┌───────────────────────────────────────────────────────┘
   ↓
   D. 디자인 구현 ──────> [게이트 A-d] ──> [게이트 C-d] ──> 사람 승인
                            토큰 준수        미적 판단
```

핵심 규칙 3가지:

1. **게이트 미통과 = 다음 단계 진입 금지.** 예외 없음. 이것이 "어떠한 상황에서도"의 구현체다.
2. **모든 단계는 `guide` 파일만 진실의 출처로 본다.** 대화 맥락에서 기준을 추론하지 않는다.
3. **`blocker`는 자동 수정 대상, `warning`은 기록만.** 심각도를 안 나누면 게이트가 무한루프에 빠진다.

## 3. 산출물

### 3-1. 가이드 (최우선 — 나머지 전부가 의존)

컨셉 문서 5장의 3계층을 파일로 떨어뜨린다.

```
guide/core.rules.json        # L1 고정불변 — 프로젝트 무관 품질 하한선 (레포 내장)
guide/README.md              # 규칙 스키마 명세
templates/project.rules.json # L2/L3 — 항목 고정, 값은 0단계 산출 (빈 템플릿)
```

규칙은 선언적으로 쓰고, 검사기가 `check.type`으로 디스패치한다.
값이 안 채워진 `blocker` 규칙이 하나라도 있으면 파이프라인 진입 자체를 막는다(fail-closed).

### 3-2. 검사기 (A단계 — LLM 아님, 코드)

`scripts/audit.js` — `use_figma`로 Figma 컨텍스트에서 실행하는 노드 순회 스크립트.
입력은 규칙 + 대상 프레임, 출력은 위반 목록 JSON.

투자 대비 효과가 가장 큰 지점이다. 코드라서 흔들리지 않고, 프로젝트마다 재사용되며,
경쟁 제품 4개 중 아무도 Figma 노드를 직접 검사하지 않는다(`concept.md` 2장) —
차별점이 정확히 여기서 나온다.

### 3-3. 2시간 안에 만들 것 — 스킬 1 + 에이전트 1 + 검사기 1

가용 시간이 2시간이면 파일 수를 늘리는 것 자체가 비용이다. 아래 3개만 만든다.

| 산출물 | 정체 | 자르지 않는 이유 |
|---|---|---|
| `scripts/audit.js` | A단계 결정론 검사기 (v0: 3개 타입) | **이게 없으면 "어떠한 상황에서도 준수"가 성립하지 않는다.** 유일한 하드 보증 |
| `.claude/skills/oss-design-harness/SKILL.md` | 오케스트레이터. W/D 분리 + 게이트 로직 + 와이어프레임·구현 지침을 **한 파일에 흡수** | 파이프라인을 잇는 유일한 접착제 |
| `.claude/agents/design-critic.md` | C단계 시각 심사 | 앵커링 방지는 서브에이전트로만 가능. 프롬프트 파일 하나라 비용이 거의 없다 |

**v0 검사기가 구현할 `check.type` 3개**: `multiple_of`(spacing 그리드),
`color_allowlist`(팔레트 이탈), `name_pattern`(네이밍).
색 대비(`contrast_ratio`)는 배경 해석(중첩 fill·투명도·그라디언트)이 필요해 2시간 안에는 위험하다.
규칙은 `core.rules.json`에 남겨두되 미구현으로 두고, **`blocker`이므로 사람 게이트로 승격**된다
(`guide/README.md` 「미구현 check.type 처리」). 침묵 통과가 아니다.

### 3-4. 2시간 스코프에서 자르는 것과 그 근거

| 자르는 것 | 근거 |
|---|---|
| `design-guide-compile` 스킬 | 자동 컴파일 대신 `project.rules.json`을 **짧은 인터뷰로 직접 채운다.** 프로젝트 1개엔 자동화가 손해 |
| `design-auditor` 에이전트 | 껍데기 비용 > 컨텍스트 절약 이득. 메인이 `audit.js`를 직접 호출 |
| `design-reviewer-persona` (B단계) | B단계는 "정답이 여럿일 때"만 필요. 통제 품질에 직접 기여하지 않음 |
| `wireframe` / `design-implement` 별도 스킬 | 오케스트레이터 `SKILL.md`의 절로 흡수. 파일 분리는 재사용 요구가 생긴 뒤에 한다 |

## 4. 작업 순서 (2시간)

| 블록 | 할 일 | 완료 판정 |
|---|---|---|
| **T+0 ~ 0:15** | `project.rules.json` 복사 후 인터뷰로 값 채우기 (그리드 단위/팔레트/네이밍 3개만 우선) | 해당 3개 규칙 `status: filled` |
| **0:15 ~ 1:00** | `audit.js` — 노드 1회 순회 + 3개 타입 dispatch + 리포트 JSON | 실제 프레임에 돌려 위반 목록이 나온다 |
| **1:00 ~ 1:30** | `SKILL.md`에 W/D 분리 + 게이트 로직 + autofix 루프(상한 3회) | 게이트 미통과 시 진행이 실제로 멈춘다 |
| **1:30 ~ 1:50** | `design-critic.md` — 인터뷰로 뽑은 C단계 기준 주입, 출력 스키마 고정 | 스크린샷 1장으로 원인 층위까지 나온다 |
| **1:50 ~ 2:00** | 관통 1회 + 남은 것 기록 | W→A→D→A→C 한 바퀴 |

**시간이 밀리면 자르는 순서(뒤부터)**: 관통 테스트 → `design-critic` →
`audit.js`의 `name_pattern`. **`multiple_of`와 게이트 로직은 자르지 않는다.**

### 6시간이 주어졌다면 추가로 할 것 (오늘 범위 밖)

`design-guide-compile` 자동화, `design-reviewer-persona`(B단계 교차 비평),
`design-auditor` 에이전트 분리, `contrast_ratio`·`variant_states_present` 검사기 구현,
후보별 페이지 분리 규약 + B단계 병렬 생성.

## 5. 리스크

- **Figma MCP rate limit** — `audit.js`는 노드를 한 번에 순회해 **1회 호출로 전체 검사**해야 한다.
  규칙마다 따로 호출하면 바로 걸린다.
- **`use_figma` 호출 전 `figma-use` 스킬 로드 필수** — 선택이 아니라 강제.
  스킬/에이전트 프롬프트에 못 박아야 에이전트가 건너뛰지 않는다.
- **동시 쓰기 충돌** — B단계 병렬 후보 생성은 후보별 페이지 분리 규약이 정해지기 전까지 보류.
- **자동 수정 무한루프** — 재시도 상한 + 초과 시 사람 에스컬레이션.

## 6. 열린 질문

- 오늘 안에 "특정 실제 화면"까지 뽑아야 하는가? 그렇다면 관통 테스트를 앞당기고
  검사 규칙 수를 3개→1개로 줄여야 한다.
- `design-critic`의 판단 기준 내용은 아직 비어 있다. 인터뷰 결과가 나와야 T+3:30 블록이
  실제 내용으로 채워진다. 그 전까지는 껍데기만 만들어진다.
